# Programs the mobile C ABI targets reject, with the exact reason they gave.
#
# One file covers ios-sim, android-arm64 and android-x64 because they share one
# boundary implementation and therefore one set of holes. If a target ever
# rejects a different set, this comparison fails and the file must be split
# rather than widened — a shared manifest that quietly accepted either set
# would hide the divergence it exists to catch.
#
# The program set is unchanged by running the corpus on a phone: each name
# below is a program the COMPILER refuses before emitting code, never one that
# built and then misbehaved. The harness compares both the file set and the
# reasons exactly, and fails on a new, removed or changed entry. An unexpected
# LLVM, clang or simulator failure is a test failure, never a skip. There is no
# regeneration flag. [IOS-TARGET-CAPABILITIES] [IOS-HOST-ABI]
#
# Three reasons appear, and they are not the same kind of limit. The corpus host
# calls only `osprey_main`, so `--entry-only` keeps internal helpers off the C
# boundary. Ordinary app archives still check all scalar exports.
#
#   * a continuation — the mobile C ABI is synchronous, so a suspended
#     continuation cannot cross or outlive a host call. Named by the OPERATION
#     that cannot be suspended, so a reader can see which effects would start
#     working if that changed [MULTI-WASM].
#   * HTTP and process spawning builtins — no iOS implementation; the Swift
#     host supplies networking and platform services through explicit imports.
#   * C ABI: an unsupported extern signature — a `Ptr` parameter has no
#     portable scalar C representation.
