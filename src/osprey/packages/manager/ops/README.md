# Registry deployment preparation

[Plan 0020](../../../../../docs/plans/0020-package-manager.md) defines the deployment stages. [environment-inventory.schema.json](environment-inventory.schema.json) defines the reviewed provisioning inventory format using JSON Schema Draft 2020-12. Prepare a separate private record for each environment; no populated inventory or cloud resources are supplied here.

Every required resource records its actual provider reference, accountable owner and evidence reference. Collection resources such as DNS records, Cloud Run services, private buckets and WAF rules must reference a versioned manifest enumerating every member. Secret entries contain Secret Manager resource names and numeric versions only; never commit credentials, connection strings, tokens or secret values. Supply database credentials through the approved mounted passfile/secret mechanism, to keep credentials out of process arguments.

The schema rejects missing entries, null/blank evidence, unknown secret fields and unpinned secret versions. Validate inventory records with a Draft 2020-12 validator before review. Schema validity only establishes record structure: reviewers must verify resource existence, distinct staging/production resources, separate privileged identities, host/callback consistency, independent custody/operators and the complete deployment acceptance evidence. Repeated owners or manifests with invented references cannot establish independence or readiness. Distinct-object checks in lists do not prove independent organizations.

The rollout's hostnames and region are proposed defaults; record approved values after checking zone access and provider availability. The API OAuth callback and Supabase provider callback are separate URLs. Do not authorize Pages preview hosts for credentialed CORS or OAuth.

Before provisioning, run `make -C src/osprey/packages registry-infra-check registry-migration-check`. The migration rehearsal needs a .NET 10-capable SDK and PostgreSQL server tools. It creates and removes a socket-only local database and checks the ownership tables, pending GitHub logins, browser sessions and public catalog. Public writes require staging verification, hosted authorization and trust services. A future Osprey deployment/rehearsal tool must validate this inventory and the actual acceptance evidence; this schema must never become a shortcut around those checks.

Build the native hosted entry point with `make -C src/osprey/packages registry-hosted-api` on the target platform. The image needs the PostgreSQL client for catalog access and OpenSSL 3 for sign-in signature verification. It reads `apiHost`, `websiteOrigin` and `edgeSecret` from the mounted `/run/registry/runtime.json`. The process binds the public API on port 8080 before opening the management listener on 8081. Only the management listener answers `GET /v1/ready` with an empty 200. The catalog returns 503 when its PostgreSQL projection is missing, malformed or expired. Hosted publication still requires the authorization and verification pipeline.

Run `make -C src/osprey/packages registry-website-check` to test the packaged Pages upload flow. The check opens the extracted site in Chromium with its generated CSP and tests signed-out, signed-in and unavailable session responses from a fixture API. It also verifies that rebuilding the ZIP from the extracted files reproduces its SHA-256.

Set `REGISTRY_API_ORIGIN` and `REGISTRY_CONTENT_ORIGIN` to the environment’s HTTPS origins and run `make -C src/osprey/packages registry-website-archive`. The build prints the content-addressed ZIP path under `target/registry-artifacts/`. The ZIP identifies the frontend bytes. Live hosted API checks and the exact-commit release audit are separate deployment gates.

The API image requires PostgreSQL client 16 or later. Terraform mounts the database CA at `/run/catalog-ca/ca.pem` and a libpq service file at `/run/catalog-service/pg_service.conf` from the pinned Secret Manager versions in `catalog_secret_versions`. Its `[catalog]` entry supplies the Supabase database host, port, database name, login and password. The API enforces TLS hostname verification. Grant the dedicated `registry_catalog_reader` login schema USAGE and SELECT on `registry.public_catalog` only. The trusted publication worker must replace or invalidate the complete public projection atomically using its signed evidence expiry. The production writer is pending.

Each projected release requires its public `publisherId` (a canonical UUID) and `publisherName` from verified release attribution. Prepare a projection with both fields before routing traffic to this API revision. Publisher profiles and credits read from that projection.

Include the validated manifest `keywords` array on each package in the public projection. The Pages website uses these keywords for its tag directory and package links. Use an empty array for a package without tags.

For each public release, project `licenseExpression` from its manifest and `notices` from the verified source bundle. Each notice includes its root filename and complete text. Use an empty array when the release has no notices. The projection can hold up to six notices per release, each up to 32 KiB. The source bundle retains all applicable license documents.

Source downloads require `published_source_bucket`, a private Cloud Storage bucket for published bundles with create-only writes. Store the canonical source bundle as `<digest-hex>.json`. The API mounts that bucket read-only and verifies the source digest and release identity against the current public projection before responding. Configure `contentHost` in the API runtime secret and set `REGISTRY_CONTENT_ORIGIN` when building Pages. Route that hostname through the protected ingress. It serves anonymous source requests without cookies or authorization headers.

The browser-session migration adds the approved Supabase subject to each GitHub binding and persists only a cookie digest and encrypted provider tokens. Apply it first to an empty registry. Any existing bindings require a verified issuer and subject backfill before enforcing the new field. The database rejects competing active bindings for one Supabase account. Its session queries reject a changed binding, principal or credential epoch, and the logout query clears the token envelope.

Add a `[session-issuer]` entry to the mounted libpq service file for the restricted `registry_session_issuer` login. Its transaction pins the cookie digest and exact issuer, Supabase subject and GitHub ID. Grant only the column-level `SELECT` needed for bindings and principals and `INSERT` for browser sessions, plus `SELECT(id)` for the new session receipt. Browser sign-in still needs session read and logout connections before production use.

Add a `[login]` entry to the mounted libpq service file for `registry_login_runtime`. This login must have no elevated role memberships. Grant schema USAGE and only column-level INSERT and SELECT on `registry.pending_logins` for `state_digest`, `browser_digest`, `verifier_envelope` and `created_at`, plus DELETE on that table. The Osprey transactions bind both digests locally and the table policies restrict the role to that pair and the ten-minute lifetime. Give the role no browser-session or ownership-table grants.

Rehearse GitHub sign-in in staging with `supabaseOrigin`, `supabasePublishableKey` and `loginKmsKey` in the runtime secret. Supply all three together and set Terraform’s `login_kms_key` to the same environment’s symmetric CryptoKey. Configure Supabase for RS256 or ES256 and a ten-minute token lifetime. The API verifies the signed `authenticated` token against the configured origin’s JWKS and matches its subject against `/auth/v1/user`.

To test session issuance in staging, set `sessionKmsKey` and Terraform’s `session_kms_key` to a separate software-protected symmetric CryptoKey. The API seals the provider tokens and commits the session before setting the browser cookie and redirecting to `/upload/`. Without `sessionKmsKey`, a successful provider exchange expires the flow cookie and returns `503 auth.session-unavailable`. Keep production sign-in disabled until staging verification and the session read and logout endpoints are ready.
