## Runaway memory (top priority)
Evidence: `/Library/Logs/DiagnosticReports/JetsamEvent-2026-11-05-090847.ips`. A compiled `tests-56195-*.out` reached 86.6 GB in about 351 s and `suite-60e67c363b6a174f.out` reached 15.6 GB in about 21 s; the Mac then stalled shutting down and rebooted at 09:12. Which program each was is reported by peers, not established here: `tests-56195` as `safetensors/tests`.
- [x] Bound the heap in `src/toolchain/compiler/runtime/memory_gc.c` and `memory_arc.c`: neither has a ceiling (the GC budget is `max(min-heap, 2 x live)`), so a runaway program grows until the OS kills unrelated processes. Check: a program allocating without end gets a typed failure with its peak size, in GC and ARC, without touching the rest of the machine. Done 2026-11-23 as [MEM-HEAP-CEILING] (spec 0018): `OSPREY_HEAP_MAX_MB`, default half of physical memory; GC collects and ARC returns its parked blocks before refusing; a full heap ends the run with status 71 and `osprey: heap limit exceeded: backend=… limit_bytes=… peak_bytes=… request_bytes=…`. Red first in `memory_gc_tests`, then green in both C suites, `a_heap_that_only_grows_ends_at_its_ceiling` (a hoarding program under 64 MiB peaks at 92 MB resident in both backends) and the corpus under GC and ARC (335/335 each). Open: Windows and WebAssembly have no default ceiling because they do not report physical memory; ending the run is a runtime quarantine, since allocation sites in compiled code have no failure branch.
- [x] [MEM-GC-SAFEPOINT] Keep the GC collecting once a fiber allocates. Under GC, the first allocation by a fiber stopped collection for the rest of the process. Check: `src/toolchain/crates/osprey-cli/tests/fiber_gc_memory.rs`.
- [ ] Find what makes each suite above grow, and fix it. Check: the suite passes under the cap in GC and ARC, with its peak recorded. Measured 2026-11-23, not reproduced: `safetensors/tests` passes under a 2048 MiB ceiling in GC and ARC, peaking at 128 MB resident in 1.7 s. `tests-<pid>-*.out` is the name `--run` gives any project folder called `tests`, so the name does not identify safetensors. `suite-60e67c363b6a174f.out` is a test-cache key over source, backend and runtime; it matches neither current safetensors key and is still unidentified. Whatever it was now stops at the ceiling.
- [x] Killing `osprey --run` leaves its compiled child running. Check: killing the parent ends the child, on every kill route the test runners use. Reproduced 2026-11-23: the CLI spawns the program and waits, and most runners kill only that one process, so all 8 cases of `killing_the_runner_ends_the_program` (GC and ARC by KILL, TERM, INT, HUP) were red. Fixed as [RUN-PARENT-DEATH] (spec TestRunner): the runner names itself in `OSPREY_RUN_PARENT` and the program's runtime ends with it; 8/8 green. Open: no watch on Windows; `run_test_corpus.sh` and the Rust test runners do not yet export their own process id, so killing one of them still leaves the `osprey` under it running until its program ends.
- [x] Make runner logs enough to diagnose this: `src/toolchain/crates/osprey-cli/tests/python_packages.rs` buffers child output and records no peak memory, deadline or program name, so the jetsam report was the only record of this crash. Check: a killed or over-cap suite logs its command, memory backend, peak RSS and elapsed time. Done in 36ec93262.

The Linux `net_runtime_tests` suite passed on checkout `ac5bd75`. [C runtime CI](https://github.com/Nimblesite/osprey/actions/runs/42527979600/job/128877403693)
- [x] #355, the rest (done: both Swift adapters pin read, list and delete through `pinnedDirectory` and `Bounded.read(parent:leaf:)`; the escape test was red first, 4/4 green after; WinUI `Store.cs` still open): 366c025ef and b0673d79e pinned only `store-write` to descriptor-relative directories. `store-read`, `store-list` and `store-delete` in both Swift `StoreAdapter.swift` copies and in WinUI `Store.cs` still resolve the name through `location()`, so a symlinked parent inside the store still reads, lists or deletes outside it. - [x] Prevent a concurrent replacement of the checked entry before the server opens it (done: `osprey_path_open.h` opens the entry with `O_NOFOLLOW`, or `FILE_FLAG_OPEN_REPARSE_POINT` on Windows, `fstat`s that handle and serves only from it; `assert_swapped_link_never_escapes` in `file_server_link_tests.c` renames a link to an outside file over the name 600 times mid-request and was red 3/3 before the fix, green 5/5 after, under ASan too; subfolders and planted FIFOs answer 404 at once).

Wired 2026-11-23: the file server is its own C suite (`file_server_tests`, no TLS), ported to MinGW (temp files and folders through `file_server_test_files.c`, Winsock deadlines, symlinks via `CreateSymbolicLinkA`; FIFO and rename-swap cases stay POSIX), and `ci-windows.yml` runs `make _test_file_server`.
