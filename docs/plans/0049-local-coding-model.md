## Phase 2 — Speed gate
- [x] [LLM-MATMUL-QUANT]: a product of a quantized matrix and a `float32` matrix, as a library kernel beside `osprey_matmul32` in `src/toolchain/compiler/runtime/gpu_device_lib.metal` with the host oracle in `gpu_host.c` (32-bit indices, `fp contract(off)`, ggml's block order so bytes match `Quant.decode`). Evidence for the design: the same Q4_K matvec takes 0.37 ms standalone (`src/osprey/examples/llms/qwen/speed/q4k_standalone.m`) against about 2 ms as a compiled Osprey kernel, so this kernel alone brings the token's products to about 0.1 s. Landed in 423d01211 as `gpuMatMulQuant` (Q4_K only): 0.42 ms per 17408×5120 product, bit-exact across the host oracle, Metal, GC and ARC; `gpu_device_tests.c` and the `buffers` twins cover it. Further block types (Q5_K, Q6_K, Q3_K, IQ4_NL, IQ4_XS, IQ3_S, Q8_0, the file's other eight) are added by name against `Quant.decode`.
- [x] Port GPT-2's handlers to `float32` as the first end-to-end proof. Done under plan 0050 Phase 4: `src/osprey/examples/llms/gpt2` in both flavors and `src/osprey/tests/core/gpu/transformer.test.*` compute in `float32` with goldens.
- [x] [LLM-DISPATCH-BATCH]: encode a token's dispatches into one Metal command buffer, waiting only where the host reads a result (`src/toolchain/compiler/runtime/gpu_metal.m`; mock and hardware suites pass, bytes match the host). Measured on the real 1×5120×17408 product: 1.62 ms per dispatch batched against 3.4 ms before, 92 Gop/s at one row (`src/toolchain/benchmarks/gpu-metal-dispatch.csv`). - [x] Reuse output buffers instead of allocating one per dispatch (the second half of the batching item). The quantized product's partial sums live in one device-resident scratch (858711b5f and after), and a dead result's Metal object now serves the next result of its size (`gpu_metal.m` pool, 64 objects, 256 MB): host time per dispatch fell from 22–32 µs to about 10 µs on the synthetic token, and `gpu_device_tests.c` proves a reused object and a dropped mapping leave a chain's words identical to the host's. The host side still allocates and zeroes a buffer per result.
- [x] Split the quantized product's inner dimension across a few threads per output for the few-row case, in a fixed block partition the host oracle mirrors, so bytes stay identical: 1, 4 or 16 parts by output count (`quant_parts` in `gpu_host.c`, `osprey_sum_parts` in the device library); 0.16–0.29 ms per 17408×5120 product and 0.165–0.22 s per synthetic token (4.5–6 tokens/s for the products) under load 10–12. Done (a): a launch whose kernel text passes no fault word to a checked helper no longer waits (`may_fault` in `gpu_runtime.c`), so a token is one batch: 32 batches for 30 tokens, 121 ms device and about 0.14 s wall per token, roughly 7 tokens/s for the products. Next: (b) vector loads of the block bytes and `x` in `osprey_matmul_q4_k` (97–130 GB/s today against ~500 available).
- [ ] Find the gap between `gpuMatMul` and the same kernel in standalone Metal at 64 rows (36–49 vs 64–97 Gop/s), repeated on a quiet machine. At one row the gap is closed: batched `gpuMatMul` (1.62 ms) is faster than the unbatched standalone run (2.7 ms).
- [ ] Synthetic workload with the real tensor shapes and 26G operations per token, on random weights. First slice done 2026-11-05: `src/osprey/examples/llms/qwen/speed/q4k_matvec.osp`, a compiled Osprey kernel decoding Q4_K blocks in-kernel on the 17408×5120 shape, bit-exact with numpy on host and Metal, about 2 ms per product batched under load 15 (`src/toolchain/benchmarks/gpu-metal-dispatch.csv`). ## Constraints
- Text-only path; port only the recurrent delta rule (not the chunked/triangular-solve form), batch every matrix product, run the state update as one sequential kernel.
- Gated DeltaNet always in `float32`.
- Attention: 24 query heads over 4 key/value heads, an output gate, rotary dimension 64 from `partial_rotary_factor` 0.25.
- Text rotary embedding must reduce to plain 1-D; the oracle confirms this before it's relied on.
- The model runs over a static Tensor effect with a host handler and a GPU handler ([PORT-DEVICE]).
- Serve on port 11435, loopback only (beside a real Ollama on 11434, which Phase 0 and the evaluation need).
- Binding llama.cpp through `extern` is ruled out: not a port under [PORT-SCOPE].
- Linux on OpenCL follows once Metal passes ([GPU-BACKEND-PORTABILITY] requires vendor neutrality).
