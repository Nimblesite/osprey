## Fix map for the two speed gaps — 2026-11-07

What works today: the port generates correct text from the real Q4 weights, the server answers the Ollama and OpenAI routes from them, and every recorded activation matches torch under GC, ARC and Metal. What keeps it from agent work is speed, in two places, each with its fix mapped here and tracked by the checklist item named.

**Gap 1, cold prompts ([LLM-PROMPT-RATE], design [LLM-PREFILL], item in Phase 4).** A prompt is fed one token at a time through `Qwen3_5Model.decode`, so a 1K prompt costs 1K decode steps (about 8–12 tokens/s, where Ollama prefills at 75–200 tokens/s cold). Fix: batched prefill.
1. `Qwen3_5Model.prefill(model, cache, tokens) -> Result[Next, str]` runs `forward` over a `[T, hidden]` matrix instead of one row: every matmul already takes a `rows` argument (`gpuMatMulQuant(x, blocks, type, rows, inner, cols)`, `Qwen3_5Device`), norms and the MLP are per-row, so those change only in their row count.
2. The DeltaNet layer runs the convolution over the T new positions plus the three cached ones and the recurrent rule as one sequential kernel over the T steps (`gpuDeltaRule` today takes one step; it gets a step count and returns the T outputs and the final state). The spec already requires the recurrent rule, not the chunked one, so no triangular solve.
3. The attention layer appends T key/value rows at once and scores T query rows against cached + T keys under a causal mask (one kernel over `T × (count + T)` cells, then the existing softmax and value sum per query row).
4. Oracle: the fixture's batched run is already recorded (`MODEL_HIDDEN_VALUES` rows `BATCH..BATCH+4`, every hook row, `MODEL_LOGITS`, all from torch's chunked rule over the 8 positions), and `model_rules_agree{t}[stage]` shows it equals the cached run within tolerance. The test is `model_prefill{t}[stage]` and `model_prefill{t}_logits`: `prefill` over the 8 tokens against those rows, then one `decode` after the prefill against the cached row 8 to prove the cache the prefill leaves is the one decode would have built.
5. Server: `Completions` prefills the uncached tail of the prompt in one call and decodes from there; the checkpoint logic is unchanged. Gate: cold 1K/8K/32K prompts measured with the cache cleared, prompt tokens/s at or above Ollama's on the same quant, recorded beside [LLM-SPEED].
Estimated size: one model module (`prefill.py`, under 500 lines) plus a step count on two kernels and ~60 fixture checks; no language change. Step 0 landed 2026-11-07 14:40 (zai/glm-5.3, verified): `Qwen3_5Model.prefill(model, cache, tokens)` as the per-token reference behind the final signature, with 19 checks in `tests/prefill_cases.py` (`model_prefill8[stage]`, `_logits`, `_greedy`; `model_prefill7_then_decode[stage]`, `_logits`; `model_prefill1[stage]`; `model_prefill_empty`), 2460 golden-identical under GC, ARC and Metal; steps 1–5 replace its body with the batched pass under the same checks.
 Step 1 attempt parked 2026-11-07 15:30 (zai/glm-5.3, stopped at 22 min, not merged): its batched pass type-checked but broke 62 of 2460 checks from the first attention layer on, decode included (`model.Mixer.attention.Mixed.3` index 0 got -0.00735, want 0.00668); the diff is kept at `target/local-coding-model/wip/2026-11-07-prefill-batched-glm-wip.patch`, and the quant kernel's column-major thread order (the T rows of one column adjacent, so a weight block is decoded once per column, not once per row; same bits per output), untested, at `…/wip/2026-11-07-quant-kernel-column-major.patch`.

**Gap 2, generation slows as the context grows ([LLM-STATE-OWNED], item in Phase 1).** 12.0 tokens/s at positions 12–132 falls to 7.4 at 132–516 on the same run. `Qwen3_5Attention.appended` builds a new keys buffer and a new values buffer per attention layer per token, copying all `count` cached rows (`gpuMap` over `count × width + width` cells); at 516 positions that is 16 layers × 2 × 516 × 1,024 floats = 135 MB of fresh allocation and copy per token, growing linearly, so token cost is quadratic in context. Fix, in two steps:
1. Attribute the slope first: `OSPREY_GPU_TIMING=2` on a 512-position run (the 12-pass profile exists, `timing-8.txt`; the 512 one is owed) splits the per-token cost between the copy kernels, the attention score kernel (inherently linear in positions) and allocation/free time outside the kernels. If allocation dominates, step 2a; if the copy kernel dominates, 2b; if the score kernel dominates, the fix is a tiled attention kernel and this item is misattributed.
2a. Without a language change: fixed-capacity blocks. Keys and values live in blocks of 256 positions (`List<GpuBuffer>` per slot); a token rewrites only the current block (16 × 2 × 256 × 1,024 floats = 32 MB, constant), and the score kernel runs per block with the softmax combined across blocks (online softmax: running max and sum). Peak copy per token no longer grows; the KV cache's total size is unchanged.
2b. The real [LLM-STATE-OWNED]: a single-owner mutable buffer type (`GpuState`) with `gpuStateWrite(state, offset, rows)` returning the same storage, legal only when the compiler can prove the value is not aliased (a linear use: one consumer, no capture by an escaping closure, else a compile error), implemented in `osprey-types` (the linearity check), the runtime (in-place write, ARC refcount 1 asserted) and the Metal adapter (no copy on unified memory). It relaxes [GPU-BUFFER] for this one type and needs its own `failscompilation` cases. This is a compiler change under plan 0045's ownership work and is the durable fix; 2a is the stopgap that keeps generation flat without it.
Gate: a test measuring token time at 1K and 32K cached positions before and after; [LLM-SPEED] holds at 32K.

Order: Gap 1 first (it decides whether [LLM-ACCEPT]'s harness runs can start at all), then 2.1 and 2a, then 2b when plan 0045 lands. Neither is legwork; both are bounded, and each ships behind the fixture oracle that already exists.

## Research — the mac and cuda handlers ([LLM-KERNELS-STATIC]), 2026-11-08

This is web research only; nothing has been built or measured.

**mac handler: MLX.** MLX is Apple's MIT-licensed C++ array library for Apple silicon.
- **API:** [mlx-c](https://github.com/ml-explore/mlx-c) exposes `mlx_quantized_matmul` (packed weights, per-group scales and biases, bit width) and `mlx_fast_scaled_dot_product_attention` in `mlx/c/fast.h`. The attention call takes a `"causal"` mask and allows more query heads than key/value heads, which this model uses (24 over 4).
- **Open problem: weight format.** MLX's quantization is affine per group, not GGUF's Q4_K and Q6_K blocks. The loader must either convert the GGUF blocks to MLX groups exactly, or requantize them, which changes the weights and breaks "same quant as the baseline" ([LLM-ACCEPT]). This is settled first, with a measured oracle error.
- **Open problem: KV cache.** MLX's fused attention reads only fp16, bf16 and fp32 inputs ([mlx#3404](https://github.com/ml-explore/mlx/issues/3404)), so the KV cache stays unquantized.
- **Speed is unproven.** Reports disagree. One guide claims 3–5× faster prompt processing than Ollama, on a different model ([bestllmfor](https://bestllmfor.com/guide/mlx-vs-llama-cpp-mac-comparatif/)). Others find llama.cpp with flash attention level with or ahead of MLX on long prompts. An M5 Max report gives llama.cpp Q4_K_M 439 tok/s at 512 tokens, with no MLX prompt figure ([llama.cpp#19366](https://github.com/ggml-org/llama.cpp/issues/19366)). The first step is `mlx_lm` against `llama-bench` and Ollama on this M4 Max at 1K/4K/10K under the GPU-METAL lock. If MLX loses, MPSGraph or adapted kernels fill the gap, because "at least as fast" is the gate.

**cuda handler: NVIDIA's standard libraries on Windows.**
- **Attention:** [cuDNN fused attention](https://docs.nvidia.com/deeplearning/cudnn/latest/operations/Attention.html) covers prefill on Ampere and Ada in fp16 and bf16 with head dimension up to 256. It needs sm80 or newer and CUDA 12.
- **Products:** [cuBLASLt](https://docs.nvidia.com/cuda/cublas/#using-the-cublaslt-api) does dense fp16 and bf16 work. No standard NVIDIA library was found that multiplies GGUF Q4_K blocks directly, so the products either dequantize each weight tile to fp16 before cuBLASLt, or use llama.cpp's int8 tensor-core MMQ ([llama.cpp#7860](https://github.com/ggml-org/llama.cpp/pull/7860), MIT) as the measured fallback.
- **Kernel loading:** [NVRTC](https://docs.nvidia.com/cuda/nvrtc/index.html) and the driver API run on Windows x86_64.
- **Baseline:** llama.cpp and Ollama on the same card. For scale, community reports give about 520 tok/s of prompt processing for a 27B Q4_K_XL on an RTX 3090 ([Towards AI](https://pub.towardsai.net/running-qwen3-8-27b-on-an-rtx-4090-cde0cb4ba338)).

## Constraints
- Text-only path; port only the recurrent delta rule (not the chunked/triangular-solve form), batch every matrix product, run the state update as one sequential kernel.
- Gated DeltaNet always in `float32`.
- Attention: 24 query heads over 4 key/value heads, an output gate, rotary dimension 64 from `partial_rotary_factor` 0.25.
- Text rotary embedding must reduce to plain 1-D; the oracle confirms this before it's relied on.
- The model is written as the GPU builtins' kernels and names `GpuBuffer`; device selection is its handler, and its suite is receipted on the host and on Metal ([PORT-DEVICE], as amended 2026-11-07).
- Serve on port 11435, loopback only (beside a real Ollama on 11434, which Phase 0 and the evaluation need).
- Binding llama.cpp through `extern` is ruled out: not a port under [PORT-SCOPE].
- Linux on OpenCL follows once Metal passes ([GPU-BACKEND-PORTABILITY] requires vendor neutrality).

## Testing and CI
- CI (Linux + macOS, existing Build → Test → Coverage phases): Phases 1, 3, 5, 6, 7 against the tiny checkpoint; fixtures stay within a few MB; CI never downloads real weights.
- Local only: real weights, the logit comparison, the memory gate and the evaluation, results in dated reports.
- `OSPREY_GPU` defaults to the host, so a device claim needs `OSPREY_GPU=metal` on the command and a receipt that shows completed dispatches.
