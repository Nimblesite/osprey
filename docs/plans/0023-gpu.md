# Plan 0023 — GPU computation and graphics backends

Contract: [0034 — GPU computation](../specs/runtime/0034-GPUComputation.md) · [0037 — arithmetic effects](../specs/language/0037-ArithmeticEffects.md) · [graphics README](../../src/osprey/examples/graphics/README.md) (graphics contract until a spec lands)
Depends on: [0037-osprey-native](0037-osprey-native.md) (WinUI host for the graphics-scene window)

## Prerequisites in place

- Metal and OpenCL execute admitted kernels and `gpuMatMul` via the shared device dialect (`src/toolchain/compiler/runtime/gpu_f64.metal`, `gpu_math64.metal`, `gpu_math_ext.metal`, `gpu_device_lib.metal`) and dispatch contract (`src/toolchain/compiler/runtime/gpu_device.h`); buffers stay device-resident between launches ([GPU-BACKEND-DEVICE], [GPU-BUFFER-RESIDENT]).
- `gpuScan` and `gpuFilter` have no device form and decline as a whole (`src/toolchain/crates/osprey-codegen/src/gpu.rs`).
- GPT-2 generation and training run every kernel and product on the selected device (`GPU=auto`, `src/osprey/examples/llms/gpt2/model/backends.osp`); `GPU=host` is the oracle. Half A is done; the 2× native-reference gate (Half B) is not.
- `src/osprey/examples/graphics/`: Metal renders on macOS; the D3D12 bridge draws every scene in software (WARP) only — no hardware adapter, and the Win32 window path (`ospgfx_d3d12_window.c`) still ships.

## Stage 4 — device coverage gates

- [ ] `gpuScan` device form [GPU-SCAN]: emit the sequential scan as the fold shape in `src/toolchain/crates/osprey-codegen/src/gpu_device/` and drop the `declined(cg, "gpuScan has no device form yet")` call in `src/toolchain/crates/osprey-codegen/src/gpu.rs`; acceptance: `src/toolchain/crates/osprey-cli/tests/cross_flavor_ir_equiv/device.rs` shows a `osprey_gpu_launch` for `gpuScan` instead of a decline, host goldens unchanged.
- [ ] `gpuFilter` device form [GPU-FILTER]: stream compaction needs a kept-count channel in `src/toolchain/compiler/runtime/gpu_device.h` (`OspreyGpuDispatch`); drop the `gpuFilter has no device form yet` decline; same acceptance as `gpuScan`.
- [ ] Preserve recovering `Arith` policies in selected-device regions [ARITH-DEVICE-RECOVERY]: integer-overflow probes under a wrapping handler recover on the host but abort on Metal/OpenCL; keep the no-trap contract and the fault tests in `src/toolchain/compiler/runtime/gpu_device_tests.c`. Measured 2026-11-05: forced Metal now returns a handled `Error` here, not an abort (`kernel: osprey_kernel_72: division by zero, which no device kernel can hand to an Arith policy`), but the host recovers and the device does not, so `mlkernels` still fails on Metal (0050-sized-numeric-types.md). The same gap applies to `Qwen3_5Device.wrapping`, which only works on the host.
- [ ] Transcendental determinism decision [FLOAT-IEEE-RESULTS]: evaluate one shared host/device `exp`/`ln`/`tanh`, measure its CPU cost and verify exact cross-platform results before claiming them; the sampled tolerances in `src/toolchain/compiler/runtime/gpu_shader_tests.c` prove no universal correct rounding. 2026-11-05: the `float32` `exp` and `tanh` in generated kernels no longer round from the 128-bit binary64 routine (about 70 µs per call on Metal, 45 ms of a 27B token); `gpu32_exp`/`gpu32_tanh` in `gpu_device_lib.metal` are one binary32 algorithm compiled for host and device, within 2 ulps of the binary64 reference. Host and Metal agree bit for bit on the shader suite; exactness across other vendors is still unverified, so the item stays open.
- [ ] Kernel-to-kernel fusion and capability negotiation beyond the two adapters ([GPU-BACKEND-HOST] fusion gap; [GPU-BACKEND-PORTABILITY] explicit negotiation). **Plan 0049:** its first requirement here, [LLM-DISPATCH-BATCH], has landed, so this item no longer blocks its model port. Merging kernels remains a lever for [LLM-SPEED], which `qwen.py` has measured but the package has not. Dispatch batching landed on 2026-11-05 in `src/toolchain/compiler/runtime/gpu_metal.m`: the one-row 5120×17408 product went from 3.4 ms to 1.62 ms per dispatch (`src/toolchain/benchmarks/gpu-metal-dispatch.csv`), which unblocks 0049's gate measurement. Later the same day (52907d9db): kernels whose text passes no fault word no longer wait per launch, the adapter commits segments of 64 dispatches and waits only where the host reads, the output-object pool reuses dead results, and `OSPREY_GPU_TIMING=2` records per-dispatch device times from timestamp counters (`bf47b2751` tests the counter fallback). With these, 0049 measured the real 27B token at 99 ms of device time and 8.92 tokens/s wall through its one-file program; a profile of one token still shows 2230 dispatches, 47 generated kernels per layer, and about 7% of device time between batches. Merging kernels into one, and capability negotiation, remain open. The 2230-dispatch profile is `qwen.py`'s; the package's kernels differ and have never been profiled on a real token.
- [ ] Profile the package model's real token with `OSPREY_GPU_TIMING=2` once 0049's GGUF loader exists, and compare dispatches and device time with `qwen.py`'s 2230 and 102 ms. Any increase is a regression to fix before merging kernels.
- [ ] Device-index arithmetic without workarounds: the Qwen kernels use `wrapAdd`, `wrapMul` and hand-written reciprocal `quot`/`rem` (`src/osprey/examples/llms/qwen/model/src/device.py`) because a checked operation passes a fault word and a launch with a fault word waits (`may_fault` in `gpu_runtime.c`). The divisors are run-time widths the host already knows are non-zero: let a kernel take such a divisor without a fault word, prove host and device agree, then delete `Div`, `quot` and `rem` from the package.
- [ ] Make the selected device visible: `OSPREY_GPU` unset means the host oracle, so a green `osprey test` says nothing about a device. A 2026-11-05 Qwen result was first reported without this distinction. `osprey test` should name the adapter in its summary, with a test for host and Metal.
- [ ] Add a required forced-Metal lane for `src/osprey/packages/transformers/tests` beside the core GPU corpus. Hand-run receipts: 2532 of 2532 on Apple M4 Max under gc and arc, `target/local-coding-model/runs/2026-11-05_171210-transformers-metal-{gc,arc}.txt`.
- [ ] Host and Metal differential over a real workload: compare the Qwen stages' bytes between the two, or record the tolerance per stage with its reason ([FLOAT-IEEE-RESULTS]). The suite shows each is within tolerance of torch, not that they match each other.
- [ ] Vendor-neutral substrate checkpoint [GPU-BACKEND-PORTABILITY]: record the shared device representation and launch/transfer interface for Metal, SPIR-V and WebGPU (optional CUDA must not determine the common ABI or require CUDA tooling), with benchmark evidence.
- [ ] CI with and without GPUs: adapter code compiles on its platforms; hardware lanes verify completed device dispatch and host parity on Apple, AMD, Intel, NVIDIA. A CUDA-only lane cannot close portable GPU delivery.
- [ ] Benchmark gate: within 2× of a native reference on the same GPU at matching precision for stencil + reduction micro-benchmarks AND GPT-2 Half B before the device flag is promoted; record numbers in `src/toolchain/benchmarks/`.

## Investigation — MLIR as the device and ML lowering path

Open question: should Osprey keep its hand-rolled GPU and ML lowering, or replace it with [MLIR](https://mlir.llvm.org/)? The hand-rolled path is `gpu.rs`, `gpu_kernel.rs`, `gpu_device.rs`, the Metal and OpenCL device dialect files and the per-backend runtime adapters. The rest of this plan (kernel fusion for [LLM-SPEED], SPIR-V and WebGPU for [GPU-BACKEND-PORTABILITY], rank-2/3 index spaces, autodiff) is work MLIR's existing dialects and passes already do. This section only decides; it builds nothing. [STAGE-DIALECT-INDEPENDENT] and plan 0016 still apply: MLIR may be a backend, but it never changes source semantics.

- [ ] Map every device construct to an upstream dialect and record each gap: `gpuMap`/`gpuZipWith` → `linalg.generic` (parallel), `gpuFold` → `linalg.reduce`, `gpuScan`/`gpuFilter` (no device form today) → `scf` + `gpu` (or explain why not), `gpuMatMul`/`gpuMatMulQuant` → `linalg.matmul` plus a Q4_K dequantize op, and buffers → `memref`/`tensor` with [GPU-BUFFER-RESIDENT] residency.
- [ ] Checked arithmetic: design `osprey.checked_*` ops whose dialect conversion lowers to overflow-flagged `arith` plus the `Arith` handler's recovery path, so [ARITH-TOTAL] holds on every device. This is the one construct with no upstream equivalent.
- [ ] Prototype: lower one admitted kernel (the GPT-2 GELU map) and one product through `linalg → scf.parallel → gpu → nvvm/spirv`, and diff the output against the host goldens and the current Metal path.
- [ ] Measure: dispatch count and device time per GPT-2 / Qwen token against the 2230-dispatch, 99 ms baseline above. MLIR's fusion (`linalg` elementwise fusion, tiling) is the main reason to switch, so the prototype must show it.
- [ ] Cost: build and ship size of the MLIR C++ libraries, the maturity of Rust access through [`melior`](https://github.com/raviqqe/melior) or the C API, the Windows (MSVC) and wasm32 toolchains, and CI time. The release (Shipwright, Homebrew, Scoop) must not need a user-installed LLVM/MLIR.
- [ ] Metal: MLIR has no Metal target. Decide between SPIR-V → MSL (SPIRV-Cross) and keeping the Metal emitter, and measure the cost against today's native path on Apple GPUs.
- [ ] Where MLIR enters the pipeline: (a) a GPU-only backend fed from the typed AST at the existing kernel-extraction seam ([GPU-KERNEL-EXTRACT]); (b) an Osprey dialect for the whole program, with effects, handlers and static discharge as conversion passes ([EFFECTS-STATIC-DISCHARGE]); or (c) MLIR types and ops carried in the AST. Recommendation to test first: (a). (c) couples the language core to a C++ framework and breaks [STAGE-DIALECT-INDEPENDENT].
- [ ] Decision record: keep, replace, or hybrid (MLIR for device code, hand-rolled host LLVM IR). If MLIR replaces the GPU path, list the files that get deleted. Do not keep two parallel kernel lowerings (duplication is a bug).

## Constraints

- No signed 64-bit division on a device: divide unsigned magnitudes only; never use a Metal device across `fork` (test aborts with mock adapters).
- A kernel's captures decide its device form: pass buffers and scalars, and read the recorded reason when a device run aborts.
- A new combinator sits on the existing chassis (`kernel_of`, `map_into`, `reduction`, `kernel_loop`); the element rule is `gpu::is_scalar` (`src/toolchain/crates/osprey-codegen/src/gpu.rs`) — do not restate its match.
- `gpu.rs` and `gpu_kernel.rs` are near the 500-LOC cap: the next addition goes in a new module beside `src/toolchain/crates/osprey-codegen/src/gpu/buffer.rs`.
- `GOLDEN_MIN` counts programs (not cases); `GPU_MODE_MIN` counts the `src/osprey/tests/core/gpu` programs re-run under the opposite lowering; both live in `src/toolchain/crates/run_test_corpus.sh` and are never lowered.
- A new kernel lowering must be cache-keyed (`test_cache_key` in `src/toolchain/crates/osprey-cli/src/executable_cache.rs` hashes `OSPREY_GPU_KERNELS`).
- Twins must emit identical IR; goldens are byte-exact under GC/ARC and wasm32 (`make -C src/toolchain/website wasm` builds the wasm runtime archive — run both).
- Graphics invariant: `base/base.osp` and every `scene.osp` stay byte-identical across backends; `ospgfx_abi.h`'s static-inline helpers must be included with `-I`, never pasted; the bridge stays `-Wall -Werror`; `make -C src/toolchain/targets graphics` on Windows needs the MSYS2 UCRT64 shell.
