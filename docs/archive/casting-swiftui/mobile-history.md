# Native mobile delivery [CAST-MOBILE]

Both native apps build and run in the simulator/emulator. All three skins pass native playback journeys on both platforms against a TLS Cast receiver fixture, including exact HTTP media bytes, seek, volume, speed, stop and replay; changing skins preserves the session. Native screenshot goldens gate the ready and restarted player in visible and headless runs on both platforms. CI coverage, broader error/lifecycle cases and physical-device verification remain incomplete.

## Shared boundary [CAST-MOBILE-ABI]

`make -C src/targets/tests casting-mobile-build TARGET=ios-sim` builds the ARC runtime and the existing casting library. The other targets are `ios`, `android-arm64` and `android-x64`. The output is `build/<target>/libOspreyApp.a`. The native shell must implement `native_slice` and `native_shape`, link the Cast networking services, and drive the resident start/dispatch boundary.

`make -C src/targets/android casting-build` builds a universal ARM64/x64 APK. Both JNI libraries are relinked before packaging; a SHA-256 receipt records their archive, header, C sources, build recipe and output bytes. The installed-package gate verifies current receipts, both ELF architectures, the exact freshly stripped libraries and the machine document. It rejects missing or empty receipts, changed inputs and stale binaries. The universal APK passes the complete ARM64 native journey, unchanged goldens and Android lint, including ChromeOS ABI support. x64 execution remains unverified on this ARM64 host.

## Native screenshot checks [CAST-MOBILE-GOLDENS]

The platform test targets compare both ready and restarted captures with one reviewed reference per platform and pixel width. They crop only the neutral native host and OS bars around the Sherbet player; every player control remains in the comparison. The gate permits at most 0.5% changed pixels overall and 2% in any 64-pixel tile, with a channel difference above 24 counted as changed. The local check has a regression proving that a small missing control fails even when the overall percentage would pass. Native playback and accessibility assertions run before the image checks.

The checked references use an iPhone 17 simulator on iOS 27 at 1206 pixels wide and a Pixel 7 emulator on API 34 at 1080 pixels wide. Start the Android emulator with `-gpu swiftshader_indirect` in both visible and headless modes so the renderer is consistent. The host GPU backend produced an entirely black framebuffer while the control journey passed; the image gate correctly rejected that run. With SwiftShader, both Android modes match the reference exactly. Both iOS modes also match exactly. The visible iOS journey passes in Xcode 27's Device Hub, with native coverage and the same command, palette and screenshot gates. The shared simulator selector opens the chosen device in the selected Xcode's Simulator or Device Hub; headless targets explicitly disable opening a viewer. Tooling regressions cover both installations, paths containing spaces, missing viewers and preservation of device selection.

Use `make -C src/targets/ios/tests casting-headless` or `make -C src/targets/android/tests casting-headless` for comparison. Each platform also has `casting-update`, which runs the native journey, rewrites only the ready reference, and checks that restarting still matches it. Review the images under `src/examples/casting/goldens/<platform>` before committing an update. A missing reference or changed dimensions fails; tests never silently create a baseline. The runner uses the ffmpeg already required for its audio fixture, without an extra image-library dependency.

## Native coverage [CAST-MOBILE-COVERAGE]

The iOS test entry point enables Xcode coverage during the same native journey, then exports [coverage.json](build/ios-test/coverage.json) with `xccov`. It removes the old report before running and publishes the replacement only after checking that the Casting application target has nonzero covered lines and source-file entries. The UI test runner's own counters cannot satisfy that check.

The current report covers 1,694 of 2,860 executable native target lines, approximately 59%. `CastDiscovery.swift` covers 57 of 71 lines after adding real Bonjour discovery and rescanning; the earlier injected-only journey covered 3. This is reported line coverage of the instrumented Xcode target; it excludes the prebuilt Osprey archive and is not proof of branch coverage. Android native coverage collection and required CI coverage gates remain incomplete. No coverage threshold has been lowered.

## Receiver identity [CAST-MOBILE-RECEIVER-IDENTITY]

Receiver selection and connection routing use host and port. Friendly names are presentation text; equal names include their endpoint in the native picker so users can distinguish them. Rescanning retains the selected endpoint while it remains available. The machine keeps its display label separately, preserving the existing artwork and status text for uniquely named receivers.

Native SwiftUI pickers expose their selected display label as an accessibility value. The receiver regression first failed because XCTest read an empty value; it now reads the selected endpoint's complete label before and after the Bonjour rescan. The loaded skin journey also verifies Midnight and Poolside selections, volume changes and playback speed values. All three native iOS journeys, the original screenshot and protocol gates, and 38 Swift host regressions pass.

The iOS journey publishes two real Bonjour services with the same friendly name: one on a refused port and one on the TLS fixture's port. It verifies distinct choices, rescans and plays through the selected working service without an injected transcript. Android exercises the same equal-name case through its native picker and verifies the retained selection in the resident frame. Both full suites pass their exact media-byte, control-command, palette and zero-difference screenshot gates. The shared suite passes under GC and ARC; all four mobile archives rebuild and the refreshed physical iPhone bundle passes strict signature verification. Physical playback, discovery permission denial and disappearing receivers remain unverified. XCTest retains its result bundle and explicit screenshots; verbose system diagnostic collection is disabled so an expected failing regression does not collect a system-wide diagnostic for ten minutes.

## Native discovery fixtures [CAST-MOBILE-NATIVE-DISCOVERY]

The Android journey omits the `testReceiver` launch extra, discovers an external process registered through Android NSD, selects its advertised endpoint and casts through native TLS. The test waits for the Receiver button to display its selection before reading the resident frame, then checks that rescanning preserves that endpoint. An independent Java HTTP client fetches the actual network-bound media URL on the emulator; the host verifies the original Content-Length, MIME type, range response and exact MP3 bytes. Loopback-only fixtures retain their existing adb-forward checks and strict cleanup assertions. This avoids changing the app's interface-specific server binding to accommodate a test tunnel.

The fixture classes run outside the APK. A shared build helper compiles both the native binding guard and NSD publisher with warnings as errors, includes their nested classes, pushes read-only jars and removes them afterward. Teardown requires the NSD unregister callback before terminating the owned helper process; cleanup failures fail the journey. Nine isolated driver and artifact checks include binary HTTP parsing and shell quoting for the nested Java class, paths with apostrophes and URL metacharacters. Both complete native suites pass with seven verified media loads and seven Stops per platform, unchanged seek/volume/speed counts and zero-difference ready/restart goldens. Android lint and 38 Swift host regressions also pass. Android verification uses the ARM64 API 34 emulator; physical devices and Android 37 permission behavior remain unverified.

## Popup freshness [CAST-MOBILE-POPUP-FRESHNESS]

The real Android NSD playback journey opens the native Volume menu, then the TLS receiver sends an unsolicited change from 100% to 25%. Selecting 50% in that old menu must leave the confirmed volume at 25%; opening a fresh menu and selecting 50% must succeed. This regression failed before the callback captured its opening binding and passes with the guard. A one-shot fixture control is removed before publishing the remote update, so repeated status messages cannot conceal an invalid command. The complete protocol gate expects exactly five Android volume commands, including the fresh-menu recovery, and three on iOS; any extra stale-menu command fails the gate.

Both complete native suites pass with seven loads, seven Stops, three seeks and four playback-rate changes per platform. Ready/restart goldens remain identical, iOS palettes pass, Android lint passes and all 25 isolated driver/tooling checks pass. The universal APK also passes a final current-input and packaged-binary check. iOS reports 1,694/2,860 native app lines covered; this excludes the prebuilt Osprey library and does not satisfy the remaining CI coverage work.

## Local appearance [CAST-MOBILE-SKIN-PERSISTENCE]

The shared app publishes its actual rendered skin as the `casting.selected-skin` slice at startup and whenever that choice changes. Native hosts save that canonical value rather than predicting an event's result or decoding opaque application state. Swift's accepted-slice callback saves to app-scoped UserDefaults; Android commits to app-scoped SharedPreferences before presenting the updated tree and surfaces a failed commit through its existing error screen. Explicit launch arguments take precedence over a saved choice. Both the native Appearance menu and the themed Skin picker use this path.

The native restart regressions select Poolside, Sherbet and Midnight, confirm the selection, terminate the process and launch again without a skin argument. They assert the restored picker value or Sherbet scene. The Android driver waits for the accepted tree before killing the process; stopping it while the selected event was still queued had correctly retained the previous choice. The original regressions failed by returning to Sherbet after a Poolside selection. Both complete native suites pass with the new restart cases, unchanged protocol counts and identical ready/restart goldens. All five iOS UI tests pass, with 1,739/2,905 native app lines covered; all 44 Swift host tests, 25 driver/tooling checks and Android lint also pass. The direct host-free casting suite passes all seven journeys, but its Make target remains blocked by a deprecated Metal API in the runtime build; the repository format gate also remains red in compiler code outside this change. Recovery from damaged or wrongly typed settings, high contrast and reduced motion remain incomplete.

## Appearance recovery [CAST-MOBILE-APPEARANCE-RECOVERY]

An unavailable launch choice now becomes the validated bundled fallback in the shared machine's actual `skin` input. The app publishes that repaired choice for native persistence and emits a separate `casting.appearance-warning` slice. The native alert explains that the default appearance was restored; it does not set the playback error input or disable the player. iOS forwards the accepted warning to transient SwiftUI alert state, while Android presents a platform AlertDialog after applying the usable tree. A valid launch emits no warning.

Both native regressions cover a removed name, an empty value and a name containing XML punctuation, an apostrophe and Unicode. Android writes and reads back the real app-scoped preferences file while the process is stopped, then checks the repaired stored value. The iOS debug fixture writes the supplied value into real app-scoped UserDefaults before the production restoration path reads it. Each case acknowledges the native alert, verifies the fallback controls and launches a fresh process without the seed or a skin override. iOS additionally selects Midnight from the recovered player. The original tests failed because the fallback was silent; the new native recovery cases pass on both platforms. Malformed preference storage and non-string preference values remain unverified.
