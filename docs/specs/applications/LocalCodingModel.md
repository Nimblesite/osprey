# Local coding model [LLM]

**Status:** in delivery, 2026-11-07. Built and receipted: the GGUF reader (`@osprey/gguf`), the `qwen3_5` model and its GGUF loader (`src/osprey/examples/llms/qwen/model`), the tokenizer from the file's own tables (`@osprey/tokenizers`), the tool-call parser and mask, and the server (`src/osprey/examples/llms/qwen/server`) answering the Ollama and OpenAI routes from the real weights, with the model's reasoning returned apart from its text and the prompt cache kept across requests with checkpoints a rewritten turn reuses ([LLM-CACHE-CHECKPOINT]). Also built: the weights pull ([LLM-WEIGHTS-PULL]) and the template's tools turn, tool calls and tool responses in the server ([LLM-TEMPLATE]). Not yet met: [LLM-BASELINE], [LLM-SPEED] on a quiet machine, [LLM-PROMPT-RATE] and its design [LLM-PREFILL], [LLM-STATE-OWNED], [LLM-MEMORY], [LLM-ACCEPT]. [Plan 0049](../../plans/0049-local-coding-model.md) owns delivery and lists what each rule still lacks.

## Model and weights [LLM-WEIGHTS]

The model is [`Qwen/Qwen3.8-27B`](https://huggingface.co/Qwen/Qwen3.8-27B), revision `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`, with weights from [`unsloth/Qwen3.8-27B-GGUF`](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF), revision `4ca720788d1e01f1bff70c033e0d0028fd02e502`.

**[LLM-WEIGHTS-PULL]:** the weights are fetched by `make -C src/toolchain/targets/llms qwen-pull` (`QWEN_QUANT=UD-Q4_K_XL|UD-Q5_K_M|UD-IQ3_XXS`) into `~/.cache/osprey-llm/gguf`: the hub's tree API at the pinned revision gives the file's size and LFS SHA-256, the download resumes whatever a `.part` already holds, and the file is named `.gguf` only when its size and digest match; a mismatch deletes nothing and names the file. Tested offline against a local Range-capable hub (`qwen-pull-headless`).

The fallback is `Qwen/Qwen3.6-27B`, which has the same `qwen3_5` architecture and the identical parameter count (27,781,427,952): a weights swap that leaves the rest of this specification unchanged.

## Serving and baseline [LLM-SERVING]

Osprey serves the Ollama wire protocol itself. A real Ollama can't host this port: `ollama create` runs a GGUF on Ollama's own engines, so no Osprey code would execute. Any harness that speaks Ollama or OpenAI points at the Osprey server instead.

The port is 11435, so it runs beside a real Ollama on 11434, which the baseline and the evaluation need. It listens on loopback only.

Real Ollama stays useful as the baseline, loaded with the same GGUF so that any quality gap belongs to the port and not the weights. The `qwen3.8:27b` library tag doesn't state its quantization, so it isn't a fair baseline.

## Architecture [LLM-ARCHITECTURE]

Everything above the runtime is Python-flavor Osprey under [PORT-SCOPE](../ecosystem/0043-PythonFlavorPorts.md#what-a-port-is--port-scope). Binding llama.cpp through `extern` would not be a port, so it is ruled out; adapting llama.cpp's MIT-licensed Metal kernels into the runtime kernel library is allowed and is the fast kernel set in [LLM-KERNELS-STATIC].

Text-only path, 64 layers of `16 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))`.

- **Attention:** 24 query heads over 4 key/value heads, an output gate, and rotary dimension 64 from `partial_rotary_factor` 0.25.
- **Text rotary embedding:** should reduce to plain 1-D because all three position axes are equal. The oracle has to confirm this before it's relied on.
- **Gated DeltaNet:** a depthwise causal convolution of kernel 4 over 10,240 channels, then the delta rule, always in `float32`, then a gated RMS norm.
- **One delta rule, not two:** Transformers has `torch_recurrent_gated_delta_rule` and a chunked form with a triangular solve, documented as computing the same thing. Port only the recurrent one, batch every matrix product, and run the state update as one sequential kernel. That removes the triangular solve. The oracle checks agreement with the chunked form.

## Memory budget [LLM-MEMORY-BUDGET]

Default: **`UD-Q4_K_XL` at 64K context**. Harness overhead alone can be 5–30K tokens, so 32K is too tight for agent work.

| Item | Size | Basis |
| --- | --- | --- |
| Weights | 17.6 GB | File size, mapped read-only |
| KV cache at 64K, `float16` | 4.3 GB | 16 attention layers × 4 heads × 256 × 2 = 32,768 values per token |
| Recurrent and convolution state | 0.16 GB | 48 layers × 48 × 128 × 128, plus 3 × 10,240 per layer, in `float32` |
| 4 prompt checkpoints | 0.63 GB | One copy of the state above each |
| Working memory | 0.5 GB | Estimate, measured when real weights run |
| **Total** | **23.2 GB** | Peak RSS gate at 24 GB |

More accuracy: `UD-Q5_K_M` (19.8 GB) at 32K also totals about 23 GB. 16 GB machines: `UD-IQ3_XXS` (10.9 GB) at 32K totals about 14.4 GB; treat this as degraded. Skipped: the vision projector (0.9 GB) and MTP (1.4 GB).

## Requirements [LLM-REQUIREMENTS]

- **[LLM-BASELINE]:** the model passes enough of the tasks to be worth porting, and the report fixes the default quant and sampling. If 3.8 fails here, run 3.6. If both fail, stop: no port can beat its own weights.
- **[LLM-WEIGHTS-MAPPED]:** a read-only buffer over a memory-mapped file region, shared with the GPU without a copy on unified memory.
- **[LLM-WEIGHTS-QUANT]:** block decoders for each tensor type the chosen GGUF actually uses, listed from the file. Compare against `gguf-py` on every block of a generated fixture.
- **[LLM-STATE-OWNED]:** one mutable, single-owner state buffer for KV and recurrent state. This relaxes [GPU-BUFFER](../runtime/0034-GPUComputation.md#buffers--gpu-buffer)'s immutability for that type only, so it needs its own checks: no aliasing, and a compile error on capture by an escaping closure. Why: `appended` builds a new keys and a new values buffer per attention layer per token, copying every cached row, so token cost grows linearly with context (12.0 tokens/s at positions 12–132, 7.4 at 132–516, 2026-11-07). Design: a `GpuState` type whose `gpuStateWrite(state, offset, rows)` returns the same storage, legal only for a linearly used value (one consumer, no capture by an escaping closure, else a compile error in `osprey-types`, with `failscompilation` cases), the runtime writing in place with the ARC count asserted at one and the Metal adapter copying nothing on unified memory. Until it lands, the permitted stopgap is fixed-capacity blocks: keys and values in 256-position blocks, a token rewriting only its current block (a constant 32 MB) and the score kernel running per block with the softmax combined across blocks (running max and sum). Gate for either: token time measured at 1K and 32K cached positions, [LLM-SPEED] holding at 32K. The slope is attributed first with an `OSPREY_GPU_TIMING=2` profile at 512 positions (copy kernels, score kernel or allocation outside the kernels), since the score kernel's linear cost is inherent and would point at a tiled attention kernel instead.
- **[LLM-ARITH-IEEE]:** an `Arith` policy with IEEE semantics in kernels and a finite check on each token's logits, which faults the request instead of emitting garbage.
- **[LLM-MATMUL-QUANT]:** a product of a quantized matrix and a `float32` matrix: [`gpuMatMulQuant`](../runtime/0034-GPUComputation.md#gpumatmulquantx-gpubufferfloat32-weights-gpubufferuint8-type-string-rows-int-inner-int-cols-int---resultgpubufferfloat32-error--llm-matmul-quant), a library kernel that decodes the GGUF blocks in place, with the host oracle holding it to the same bytes below 32 rows and within a recorded tolerance from 32 rows, where Metal's SIMD-group matrix units compute a prompt chunk.
- **[LLM-DISPATCH-BATCH]:** the Metal adapter encodes consecutive dispatches into command buffers of 64 (`GPU_SEGMENT` in `gpu_metal.m`), commits each without waiting so the device runs one while the host encodes the next, and waits only where the host reads a result (a write-back or a download) or the ring of 1,024 queued dispatches is full, and then for the oldest segment alone. Bytes match the host and a failed segment is reported by its first kernel. `OSPREY_GPU_TIMING=1` prints each segment's device time; `OSPREY_GPU_TIMING=2` gives every dispatch its own encoder inside the segment and prints its device time from the timestamp counters at the encoder boundaries, the per-kernel profile that found a token's cost centres (prompt-to-response receipts: `target/local-coding-model/runs/`).
- **[LLM-SPEED]:** faster than the Ollama baseline on the same quant on the M4 Max (Ollama: median 8.0 generated tokens per second, measured 2026-11-05). Measured 2026-11-05 after the lane matmul, the binary32 `exp` and the pipelined segments: 8.92 tokens per second over 61 generated tokens, device time 99 ms per token, text identical to the earlier runs (`target/local-coding-model/runs/2026-11-05_142230-pipelined-segments.txt`). Measured 2026-11-07 through the package with Ollama unloaded (load 4.4–6.4): 12.0 tokens per second wall at positions 12–132 and 7.4 at positions 132–516, the fall being the per-token cache copy [LLM-STATE-OWNED] removes (`2026-11-07_125100-package-speed-quieter.txt`); the number on a machine with nothing else running is still owed.
- **[LLM-PROMPT-RATE]:** a cold prompt (no cache hit) is processed at least as fast as the Ollama baseline on the same quant, measured on 1K, 8K and 32K-token prompts with the cache cleared between them, and reported in prompt tokens per second beside [LLM-SPEED]. Ollama's first turns of about 1,000 tokens ran at 75–200 prompt tokens per second on the shared machine (2026-11-07, from the Q4 journal; later turns hit its prefix cache and are not cold); the port feeds a prompt one token at a time at generation speed, so this is not met until prefill is batched.
- **[LLM-KERNELS-STATIC]:** two kernel sets for the products and attention, both kept and both built: **exact**, the current library kernels, which are the reference; and **fast**, adapted from llama.cpp's Metal kernels (simdgroup-matrix quantized products and a fused flash-attention kernel). The model calls these operations only through a static effect, and a handler chosen when the program is compiled selects one set ([GPU-DEVICE](../runtime/0034-GPUComputation.md#device-selection--gpu-device), [STAGE-HANDLE-STATIC](../language/0017-AlgebraicEffects.md#static-handlers--stage-handle-static)); the sets are three handlers of that one effect, so the model code never changes: **exact** (portable reference), **fast-metal** (llama.cpp's Metal kernels) and **fast-cuda** (llama.cpp's MIT-licensed CUDA kernels: quantized MMQ/tensor-core products and flash attention, on the CUDA backend in [GPU-DEVICE]), so either set is compiled into the build with no run-time switch, no environment variable and no dispatch cost. The same tests run against both builds: each fast build's activations stay within [LLM-MODEL-ORACLE]'s tolerance of the exact build on the same prompts, and every prompt-rate and speed receipt names the build it measured, beside Ollama's rate on the same prompts. Sources the fast sets adapt from (MIT): llama.cpp's [ggml-metal](https://github.com/ggml-org/llama.cpp/tree/master/ggml/src/ggml-metal) and [ggml-cuda](https://github.com/ggml-org/llama.cpp/tree/master/ggml/src/ggml-cuda) kernels, specifically the CUDA int8 tensor-core MMQ ([llama.cpp#7860](https://github.com/ggml-org/llama.cpp/pull/7860)), the few-row MMA ([llama.cpp#31533](https://github.com/ggml-org/llama.cpp/pull/31533)) and the `mma` FlashAttention ([llama.cpp#11583](https://github.com/ggml-org/llama.cpp/pull/11583)); the CUDA adapter loads PTX through the driver API, compiled by [NVRTC](https://docs.nvidia.com/cuda/nvrtc/index.html). The fast-cuda build's prompt-rate baseline is llama.cpp on the same NVIDIA host; research and steps are in [plan 0049](../../plans/0049-local-coding-model.md).
- **[LLM-PREFILL]:** the uncached tail of a prompt is processed as one batch, not one `decode` per token: `Qwen3_5Model.prefill(model, cache, tokens)` runs the forward pass over a `[T, hidden]` matrix (every matrix product already takes a row count), the DeltaNet convolution over the T new positions plus the three cached ones, the recurrent delta rule as one sequential kernel over the T steps returning the T outputs and the final state (still the recurrent rule, never the chunked one), and attention with T query rows against cached + T keys under a causal mask. The cache a prefill leaves must be the cache T decodes would have built: the oracle is the fixture's recorded batched run (`MODEL_HIDDEN_VALUES` rows `BATCH..`, every hook row, `MODEL_LOGITS`) followed by one `decode` against the cached row after them. This is how [LLM-PROMPT-RATE] is met.
- **[LLM-MODEL-DELTANET] / [LLM-MODEL-ATTENTION] / [LLM-MODEL-ROPE] / [LLM-MODEL-CACHE]:** the `qwen3_5` text model split across `src/osprey/examples/llms/qwen/model/src/*.py` (`deltanet.py`, `attention.py`, `rope.py`, `cache.py` and their neighbours).
- **[LLM-MODEL-ORACLE]:** all activations within tolerance, on host and GPU handlers. This is what CI runs, and CI never downloads real weights. Host and Metal are not bit-identical and are not required to be: measured 2026-11-07 over all 251 buffers the fixture suite reads back, 29% of elements identical (embeddings, rotary tables, norm tables, `slice`/`zeros`/`added`), layer outputs within 2.2e-8 absolute at every position, the final norm within 2.2e-6 on values near 3, logits within 6e-7, because the Metal matmul sums each row across lanes in a different order from the host and Metal's transcendentals round differently (`sigmoid` 1 ulp); both stay inside the torch tolerance (rtol 1e-5, atol 1e-6), which is the gate (`2026-11-07_133000-host-vs-metal-bits.txt`).
- **[LLM-MEMORY]:** peak RSS at or under 24 GB at full context, measured by the test. A local gate, since hosted runners can't hold this model.
- **[LLM-TOKENIZER]:** NFC, the split pattern and ByteLevel in `@osprey/tokenizers`, using `@osprey/tiktoken`'s merge code so it isn't duplicated. Read the vocabulary and merges from GGUF metadata if the file is confirmed to hold them, so one file is enough.
- **[LLM-TOOL-PARSE]:** a streaming parser for the template's `<tool_call><function=…><parameter=…>` format, coercing values by the tool's JSON Schema. Separate `<think>` content from replies.
- **[LLM-TOOL-CONSTRAIN]:** once the model opens `<tool_call>`, mask tokens so that only declared function names, declared parameter names, and values valid for enum, number and boolean types can be sampled. Free text stays free. Implement as a logits processor.
- **[LLM-TOOL-REPAIR]:** a call that still fails its schema goes back to the harness as a tool error it can recover from, never as made-up arguments.
- **[LLM-API-OLLAMA]:** `/api/version`, `/api/tags`, `/api/show` (reporting capabilities and context length), `/api/ps`, `/api/chat`, `/api/generate`, with NDJSON streaming and `tool_calls` arguments as JSON objects.
- **[LLM-API-OPENAI]:** `/v1/models` and `/v1/chat/completions` with SSE.
- **[LLM-TEMPLATE]:** the served prompt is what the GGUF's own `tokenizer.chat_template` writes, byte for byte, for everything the server renders: the `# Tools` system turn with each tool as jinja2's `tojson` writes it (keys sorted at every level, `", "` and `": "` separators, ASCII only, `<`, `>`, `&`, `'` as `\u` escapes), the call-format instructions, the merged leading `system`/`developer` text, an assistant history turn's `<tool_call>` blocks (a string argument verbatim, any other as `tojson`) and a `tool` message's `<tool_response>` inside one user turn per run of tool messages; Ollama refuses string arguments and missing names with 400. OpenAI decodes serialized argument objects at the wire boundary before rendering. Nonempty strings that fail to decode to an object still receive the template’s 400. With `preserve_thinking=false`, assistant turns after the latest user query keep their thinking frame and older turns drop it. The generation prompt ends at `<|im_start|>assistant` and its newline so the model's reasoning arrives in the reply. The tests render through a committed copy of the template (`server/tests/chat_template.jinja`, under the model's Apache-2.0 notice) and compare token counts and continuations against it, never against a string the server was handed.
- **[LLM-API-QUEUE]:** one generation at a time with a FIFO queue, cancelled when the client disconnects.
- **[LLM-API-LIMIT]:** a prompt over `num_ctx` is an error naming both numbers. Never truncate silently; a harness that loses its instructions gives wrong answers with no warning.
- **[LLM-CACHE-CHECKPOINT]:** the KV cache can be cut back but recurrent state can't, so keep rolling checkpoints of the state and reuse the longest matching prefix.
- **[LLM-ACCEPT]:** on the same GGUF, task pass rate within 1 of the 30 against the Ollama baseline; no schema-invalid tool call reaches a harness; the 24 GB and speed gates still hold.

## Scope [LLM-SCOPE]

Vision and video, MTP, training, producing our own quantizations, YaRN beyond 262K, CUDA, batching for several users, and Windows are out of scope. Linux on OpenCL follows once Metal passes, since [GPU-BACKEND-PORTABILITY](../runtime/0034-GPUComputation.md#vendor-independence--gpu-backend-portability) requires vendor neutrality.
