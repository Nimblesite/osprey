# Native GPU Integration for Osprey: A Research Foundation

## TL;DR
- **A native GPU story for Osprey is achievable and defensible**: encode GPU memory spaces and host/device separation directly in the Hindley-Milner type system, expose data-parallel combinators (map/reduce/scan/stencil) as first-class constructs that lower through a Futhark-style flattening/fusion pipeline onto an MLIR backend (gpu/nvgpu/nvvm dialects), and reuse Osprey's existing uniqueness/ownership analysis and algebraic-effect system to make GPU memory and side effects compile-time-checked. This directly targets Mojo's biggest weaknesses (no ADTs/sum types/pattern matching, closed compiler until Fall 2026, low-level CUDA-like kernel model).
- **Osprey should differentiate from Mojo on three axes**: (1) a *purely functional, effect-typed* data-parallel model where illegal memory-space access and unhandled GPU effects are type errors, versus Mojo's "performance over safety" thread-level model; (2) ADTs + pattern matching + HM inference that Mojo lacks entirely (its December 2025 roadmap defers `match` and enums to 1.x releases after the May 7, 2026 1.0.0 beta); (3) an open, spec-first design versus Mojo's compiler that Modular has "committed to open-sourcing... in Fall 2026." Osprey's closest academic relative is **Futhark** (statically-typed, purely functional, uniqueness types, incremental flattening), and the strongest design lessons come from Futhark, Dex (typed indices + Accum effect for parallel autodiff), Accelerate, and Triton (tile-level model).
- **The central design tensions are real and must be chosen deliberately**: functional purity vs. GPU performance (solved partially by uniqueness types + in-place updates + Accum-style effects), portability vs. NVIDIA-optimality (solved by an MLIR progressive-lowering pipeline where `gpu`→`nvgpu`→`nvvm` gives NVIDIA-optimal codegen while `gpu`→SPIR-V/ROCm preserves portability), and ergonomic implicit parallelism vs. explicit schedule control (Halide/Exo separation of algorithm and schedule is the model to emulate).

## Key Findings

### On Osprey's existing design (from the spec)
Osprey is a statically-typed functional language with: Hindley-Milner type inference; algebraic data types and pattern matching; immutable-by-default values with a `mut` rebinding that never mutates heap values in place; **algebraic effects with compile-time exhaustive handling** (unhandled effects are compile errors, effect inference computes a minimal effect set, functions are pure unless annotated `!E`); an **ownership/uniqueness-based memory model** where the compiler infers ownership, statically places frees at last use, and only "shared residue" carries non-atomic reference counts — plus a `--static-memory` mode that fails compilation wherever a refcount would be inserted (giving "Rust-class output without a borrow checker"); an acyclic value heap; fiber isolation (share-nothing, move/copy across boundaries); an LLVM backend plus a WebAssembly target; a typed C FFI; and two syntax flavors (Default `.osp` and an ML flavor) that both lower to one flavor-blind canonical AST. This is an unusually good substrate for native GPU support: purity + effects + uniqueness types are exactly the ingredients Futhark and Dex use.

### AREA 1 — Language design for native GPU support

**Memory-space-aware types.** GPUs expose distinct address spaces — global, shared (per-block), local/private (per-thread), constant, and registers. In NVIDIA's model these are physically different memories with different visibility and latency. The MLIR/NVVM dialect "introduces NVIDIA extensions to the MLIR/LLVM type system and address spaces (e.g., global, shared, and cluster memory)," and at the hardware level memory-space qualifiers become LLVM address-space annotations. Research on encoding these in a source type system is well-established: address-space qualifiers in OpenCL C, and typed-IR work (e.g., CuLifter's lifting of SASS where "memory-space qualifiers become LLVM address-space annotations"). The design opportunity for Osprey: make address space a *type parameter* (e.g., `Array[Global, f32]`, `Shared[f32]`) so that a thread-private value flowing into a global store, or a shared-memory access outside a synchronized region, is a compile-time type error rather than undefined behavior. This is stronger than Mojo, whose docs explicitly state "when there's a tradeoff between GPU performance and safety or ergonomics, performance takes priority."

**Host/device separation.** Two traditions exist: single-source (CUDA C++, SYCL, Mojo — host and device in one language, kernel launch as a library call) and staged/embedded (Accelerate, JAX — device computations are a distinct type `Acc a`/traced jaxpr, compiled at runtime). Accelerate "distinguishes between vanilla arrays (in Haskell memory on the CPU) and embedded arrays (in device memory on a GPU)" via the `Acc` type constructor. Osprey's effect system offers a third, cleaner path: model "device code" as a computation in a `Gpu` effect (or a `Device` region), so the type-and-effect discipline already in the language enforces that device-only operations cannot be performed in host context and vice versa, with the same machinery that already rejects unhandled effects.

**Data-parallel primitives as first-class constructs.** The functional-array tradition (NESL, Data Parallel Haskell, Accelerate, Futhark) expresses parallelism through a small set of second-order array combinators — map, reduce, scan, filter, gather/scatter, segmented scan, stencil — rather than explicit threads. Futhark's core provides "map, reduce, filter, and scan" (SOACs — second-order array combinators) plus `redomap`/`stream_red` for strength-reduced fused reductions. Blelloch's NESL pioneered nested data parallelism with the **flattening/vectorization transformation** that converts nested parallelism into flat data parallelism (segmented operations + flag/segment-descriptor vectors); this is the theoretical bedrock. Futhark's **incremental flattening** (Henriksen et al., PPoPP 2019) generates multiple code versions at different parallelization levels and picks at runtime, avoiding the classic flattening pathology of increased asymptotic work.

**Effect systems for GPU side effects.** Dex is the key reference: its `for` builds arrays and runs in parallel because iterations are independent, but effects change this — the general `State` effect "cannot be evaluated in parallel anymore," so Dex adds a **parallelism-friendly `Accum` effect** (write-only, monoidal, "essentially isomorphic to the Writer monad") that *preserves* parallelism and is exactly what reverse-mode autodiff needs. Dex's effect system was "hugely inspired" by Koka (Leijen). Osprey already has Koka-style algebraic effects; the direct lesson is to classify GPU-relevant effects into parallelism-preserving (Accum/reduction) vs. parallelism-destroying (general State) and let the effect type dictate whether a `map`/`for` is legal to offload. The state of the art for combining general algebraic effect handlers with parallelism is **"Parallel Algebraic Effect Handlers"** (Xie et al., ICFP 2024, Dex-inspired), which gives a formal account of which handler shapes commute with parallel evaluation — the closest existing theory to what Osprey needs, since Osprey's handlers are exactly the construct being parallelized.

**Automatic differentiation as first-class.** This is a competitive necessity against Mojo/JAX/Dex. Dex's "Getting to the Point" (Paszke et al., ICFP 2021) shows index sets + parallelism-preserving autodiff; JAX provides `grad`/`vmap`/`jit` as composable functional transformations over a functional trace; Slang.D (Bangaru et al., SIGGRAPH Asia 2023) adds "first-class automatic differentiation" to a shading language with "a differentiable type system designed to ensure type safety" and compile-time checks "to guard against common mistakes... such as dropping derivatives unintentionally." Conal Elliott's "The Simple Essence of Automatic Differentiation" (ICFP 2018) gives the categorical foundation well-suited to a functional language.

**ADTs and functional constructs on GPUs.** This is the hard research frontier and Osprey's biggest differentiator *and* biggest risk. Sum types, pointers, closures, and recursive data are awkward on SIMT hardware. NESL's flattening was "concerned solely with first-order multidimensional arrays containing primitive types," later extended "to handle higher-order and recursive data types in the work on Data Parallel Haskell" (Keller, Chakravarty et al.), and further in "Data-Only Flattening" (Bergstrom, Reppy, Rosen, Shaw et al., PPoPP 2013). The practical lesson from every high-performance system (Futhark, Accelerate) is to restrict *device* code to a regular, first-order, statically-shaped array sublanguage, while allowing full ADTs/higher-order functions in *host* code and at kernel boundaries. Osprey can use its two-flavor/one-AST design to define a device sublanguage as a typed subset.

**Uniqueness/linear types for GPU memory.** Futhark introduces "a simple type system for in-place updates that ensures referential transparency and supports equational reasoning" (Henriksen et al., PLDI 2017); its uniqueness types are "similar to, although simpler than, the uniqueness types of the programming language Clean." The type checker "verifies that the 'source' array a is never used on any execution path following the in-place update... [and signals] a compile time error if in-place updates are used in a way where safety cannot be guaranteed." Futhark's own designers note the feature is "somewhat unpleasant" in its interaction with other features — a caution for Osprey. Osprey already has an ownership/uniqueness analysis and a `--static-memory` mode; extending this to device buffers (no GC on the GPU, deterministic frees, in-place updates for coalesced writes) is a natural fit and avoids Mojo's manual `DeviceBuffer` lifecycle.

**Syntax ergonomics.** Triton "flips the conventional CUDA model": instead of scalar per-thread code, programs "operate on tiles of data... with the compiler handling thread mapping, shared memory allocation, and register usage," which "effectively abstracts away all the issues related to concurrency within CUDA thread blocks (e.g., memory coalescing, shared memory staging)." Chapel exposes GPU parallelism simply through `forall`/`foreach` loops on GPU sublocales. The ergonomics spectrum runs from fully implicit (Accelerate/Futhark combinators, Chapel loops) to tile-explicit (Triton) to thread-explicit (CUDA/Mojo). Osprey should default to implicit combinators with an optional tile-level escape hatch.

### AREA 2 — Compiler and backend

**MLIR is the decisive substrate.** Mojo's central advantage is being "the first language based on the LLVM's Multi-Level Intermediate Representation (MLIR)." MLIR is organized around dialects that are "progressively lowered (through a sequence of rewrite passes) toward successively lower-level dialects." The relevant GPU dialects form a clean stack: the target-agnostic **`gpu`** dialect (retargetable, lowers to NVIDIA and AMD), the **`nvgpu`** dialect that "functions as an intermediary... connecting higher-level target-agnostic dialects like gpu and vector with the lower-level NVVM dialect" and exposes TMA/async copies/`ldmatrix`, and the **`nvvm`** dialect (thin, near-mechanical mapping to NVVM/LLVM intrinsics, covering "warp-level collectives... matrix/tensor core operations (e.g., mma.sync, wgmma), tensor memory accelerator (TMA) operations"). The `gpu-lower-to-nvvm-pipeline` "lowers primary dialects (arith, memref, scf, vector, gpu, and nvgpu) to NVVM," with options like `cubin-chip=sm_90a cubin-features=+ptx80`. Higher dialects `linalg`, `tensor`, `affine`, `vector`, `memref` provide structured lowering. **Recommendation: build Osprey's GPU backend on MLIR to neutralize Mojo's core advantage** while reusing the whole ecosystem.

**Polyhedral compilation.** For affine loop nests, the polyhedral model enables automatic tiling, parallelization, and locality optimization. PPCG (Verdoolaege et al., TACO 2013) is "a novel source-to-source compiler" that accelerates "any static control loop nest, generating multiple CUDA kernels," with "a multilevel tiling strategy." Pluto pioneered the tiling/fusion algorithm; Baskaran's C-to-CUDA was "the first end-to-end, automatic source-to-source polyhedral compiler" for GPUs; Polly brings polyhedral optimization to LLVM IR. These are most useful for the loop-based parts of a device sublanguage.

**Separation of algorithm and schedule.** Halide's core contribution "separates the algorithm — what to compute — from the schedule — how to compute it," enabling per-platform tuning without changing the function. TVM extends this to tensor programs; Exo (and Exo 2, "Growing a Scheduling Language," 2024) push scheduling into user-definable rewrites with cursors. Halide autoscheduling (Adams et al., SIGGRAPH 2019; Mullapudi et al. 2016; Li et al. GPU autoscheduler 2018) uses beam search + learned cost models and is "the first automatic scheduling algorithm to significantly outperform human experts on average." Osprey's opportunity: keep the functional combinator program as the *algorithm* and expose schedules (tiling, fusion, memory placement) as a separate, optional, typed layer.

**Code generation for the memory hierarchy.** Effective GPU codegen requires tiling, memory coalescing, shared-memory staging, bank-conflict avoidance, and register allocation. Triton's compiler "automatically handles memory coalescing, shared-memory management, and tensor-core scheduling." Futhark's compiler applies "fusion, flattening, distribution, tiling" to "shield the programmer from... the underlying hardware." Kernel fusion is critical to minimize host↔device traffic; XLA's operator fusion and Accelerate's array fusion (McDonell et al., "Optimising Purely Functional GPU Programs," ICFP 2013) are the functional-world exemplars.

**JIT vs AOT.** Accelerate, JAX, Taichi, and CUDA.jl are JIT (runtime specialization to shapes/hardware); Futhark and Mojo support AOT. The ORNL study of Mojo found "no meaningful differences between JIT and AOT kernel executions" because Mojo forces performance-critical information to compile time. A functional language benefits from JIT specialization on array shapes; Osprey should support both, defaulting to AOT for deployment and JIT for shape-specialized kernels.

**Progressive lowering for a functional source language.** The recommended pipeline: Osprey AST → a high-level Osprey array dialect (SOACs, shapes, effects) → fusion/flattening/scheduling passes → `linalg`/`affine`/`vector`/`scf` → `gpu`/`nvgpu` → `nvvm`/ROCDL/SPIR-V → LLVM/PTX/cubin. This mirrors how Julia's GPUCompiler.jl "takes native Julia code and compiles it directly to GPUs" via LLVM, and how Triton's MLIR backend generates PTX.

### AREA 3 — CUDA/NVIDIA interop and ecosystem

**Library interop.** The proven strategy (Julia's CUDA.jl) is to pair native codegen with FFI bindings to vendor libraries: CUDA.jl offers "comprehensive integration with vendor libraries including cuBLAS, cuFFT, cuSOLVER, cuSPARSE, cuDNN, cuTENSOR." Accelerate uses FFI bindings for BLAS/LAPACK/FFT (accelerate-blas, accelerate-fft). Osprey's typed C FFI (spec §19) is the hook; the design task is a safe, typed wrapper layer over cuBLAS/cuDNN/cuFFT/CUTLASS/Thrust with device-buffer types that integrate with the ownership analysis.

**NVIDIA-optimal codegen.** The NVIDIA-specific performance path runs through PTX/NVVM: tensor cores are programmed via the C++ WMMA API or, for full control, "inline PTX instructions mma.sync.aligned... offer a more direct way to access all features of Tensor Cores." Hopper introduced warpgroup-level `wgmma.mma_async` (128 threads, operands from shared memory); Blackwell adds the `tcgen05` family and TMA. FlashAttention-4 on Blackwell is written entirely in CuTeDSL (the CUTLASS Python tile DSL), reaching ~1600 TFLOPs/s (~71% utilization) on B200 — up to 2.7× faster than contemporaneous Triton — because at development time Triton did not expose Blackwell TMA/TMEM; that rationale is now historical, since Triton's in-tree **Gluon** DSL (`triton.experimental.gluon`) exposes TMA, mbarrier, TMEM, and tcgen05 MMA with official tutorials. The enduring lesson stands in softened form: the highest-end features resist *portable* abstraction and arrive first in layout-explicit escape hatches. MLIR's `nvgpu`/`nvvm` dialects model mma.sync, wgmma, TMA, and async copies — and as of 2025 the `nvvm` dialect includes Blackwell TMEM alloc/load/store and the tcgen05 op family — so an MLIR-based Osprey can reach these without hand-written PTX.

**Single-source portability lessons.** SYCL, Kokkos, Alpaka, and RAJA are C++ layers that achieve portability by mapping one source to multiple backends at build time. Kokkos "can use CUDA, HIP, SYCL, HPX, OpenMP and C++ threads as backend programming models," abstracting execution spaces and memory spaces with hierarchical teams/threads/vector lanes (a team "mapped to a thread block"). SYCL provides "a single-source abstraction layer enabling developers to write both host-side and kernel code in the same file" but "does not guarantee automatic and perfect performance portability." The lesson: portability is a build-time backend-selection problem, and memory/execution-space abstractions must be first-class.

**CUDA toolchain integration.** A new language must integrate with: NVCC/cicc (device compile to PTX), **nvrtc** (runtime compilation), the **PTX ISA** (virtual ISA), **cubin/fatbin** (device machine code/SASS), and the **driver API vs runtime API**. Chapel, for instance, "generat[es] and pack[s] PTX assembly and link[s] against and using the CUDA driver API at runtime." An MLIR pipeline can emit PTX/cubin directly via the `gpu-module-to-binary` pass.

**Vendor-neutral targets.** SPIR-V (Vulkan compute/OpenCL), WebGPU/WGSL, and HIP/ROCm provide the portability story. MLIR's `gpu` dialect lowers to all of these; Taichi already targets "CUDA, Vulkan, Metal, and OpenGL ES." WebGPU is no longer speculative: it ships by default in all major browsers (Safari 26 closed the gap in September 2025), and WGSL **subgroups** (SIMD-level cross-lane ops, stable in Chrome 134, February 2025) deliver 2–3× speedups on matrix-vector workloads. Osprey's existing WASM target pairs naturally with a WebGPU/WGSL backend for browser GPU compute.

### AREA 4 — Comparative analysis

**Mojo (primary comparator).** Built on MLIR; ownership model with argument conventions `read`/`mut`/`var` (formerly `borrowed`/`inout`/`owned`), transfer operator `^`, and **ASAP destruction** ("destroys values... after every sub-expression... no garbage collector"). Its GPU model is **CUDA-/HIP-like and low-level**: kernel launch is a *library call* — `ctx.enqueue_function[kernel](grid_dim=..., block_dim=...)` on a `DeviceContext`, with device memory via `enqueue_create_buffer[dtype](n)` returning a `DeviceBuffer`. Mojo docs are explicit that "performance takes priority" over safety/ergonomics. Compile-time metaprogramming uses parameters/`@parameter`/`comptime` (an old automatic `autotune` facility was removed; autotuning is now manual). **Documented weaknesses Osprey can exploit:** (1) the compiler is **closed-source** — Modular's open-source page states "The Mojo standard library is fully open-source on GitHub... We also plan to open-source the Mojo compiler in 2026," with the stdlib under "Apache License v2.0 with LLVM Exceptions" but "Modular, MAX and Mojo usage and distribution... licensed under the Modular Community License"; Modular's FAQ commits: "We have committed to open-sourcing Mojo in Fall 2026." As of July 31, 2026 the 1.0 final has NOT shipped: beta 1 landed May 7, 2026, beta 2 on June 18, 2026 (Modular 26.4), nightlies are on 1.0.0b3, and stable 1.0 is targeted for late summer 2026; (2) **no sum types/enums/ADTs/pattern matching** — per Modular's roadmap (reconfirmed mid-2026), the "match statement and enums, would follow in 1.x releases" after 1.0; (3) Python-superset "fragmentation" between AOT-compiled code and run-time-only CPython interop; (4) concrete performance and feature gaps found by Oak Ridge National Laboratory (Godoy et al., SC Workshops '25 / WACCPD, arXiv:2509.21039): **no fast-math option**, weak **atomics on AMD**, higher register usage than CUDA, no plain-old-data structs on GPU memory (required flattening an `Atom` struct into a float array), and tooling/profiling gaps. Per the paper, "On NVIDIA H100, Mojo achieves approximately 87% of CUDA's performance, attributed to CUDA's more efficient use of memory resources and fewer registers-per-thread (21 for CUDA vs. 24 for Mojo)," and its abstract concludes: "Mojo's performance is competitive with CUDA and HIP for memory-bound kernels, whereas gaps exist on AMD GPUs for atomic operations and for fast-math compute-bound kernels on both AMD and NVIDIA GPUs" (workloads: seven-point stencil, BabelStream, miniBUDE, Hartree–Fock; on H100 and AMD MI300A).

**Futhark (closest academic relative).** Statically-typed, purely functional, data-parallel array language; AOT compiler generating GPU code (originally OpenCL, now also CUDA). Uses SOACs, a **uniqueness type system for in-place updates** that "ensures referential transparency," aggressive fusion, and **incremental flattening** (PPoPP 2019) that generates multiple parallelization versions and auto-tunes/selects at runtime. Henriksen et al. PLDI 2017 is the canonical paper. Actively maintained (0.26.3, May 2026, added property-based testing; a type-checker rewrite landed July 2026); automatic differentiation and sum types are established features, though sum types on device lower to flattened representations; a WebGPU backend remains experimental. Strengths: proven high performance, machine-neutral, clean ML-family syntax. Weaknesses: no first-class irregular/nested data on device; uniqueness types have awkward interactions (per the authors). **This is the blueprint for Osprey's device sublanguage.**

**Dex.** Google research language for "typed, functional array processing" in the Haskell/ML family; **typed indices** (`n => Int` arrays), a lightweight parallel `for`, and an **effect system** distinguishing serial `State` from parallel-preserving `Accum`. Key for autodiff (Paszke et al., ICFP 2021). Lesson: index types + effect-typed parallelism are directly portable to Osprey's HM + effects.

**Accelerate (Haskell EDSL).** Embedded array language with runtime code generation; `Acc a` type separates embedded (device) from host arrays; backends accelerate-llvm-ptx (NVIDIA) and accelerate-llvm-native (CPU); collective operations as "algorithmic skeletons"; strong fusion (ICFP 2013). Related Haskell EDSLs: Obsidian, Nikola. Lesson: type-level host/device separation and aggressive fusion.

**NESL / Data Parallel Haskell / flattening.** Blelloch's NESL (CMU) established nested data parallelism + the flattening transformation to VCODE. DPH extended flattening to higher-order/recursive types. Foundational for any nested-parallel functional language; the cost-model caveat (flattening can increase asymptotic work) motivates Futhark's incremental approach.

**Julia (CUDA.jl / KernelAbstractions.jl / GPUCompiler.jl).** A dynamic language achieving native-feeling GPU codegen via LLVM: GPUCompiler.jl "takes native Julia code and compiles it directly to GPUs"; KernelAbstractions.jl provides vendor-agnostic `@kernel` functions with `@index`, `@localmem`, `@synchronize` that run on CUDA/ROCm/oneAPI/Metal; CUDA.jl wraps cuBLAS/cuDNN/etc. Lesson: pair a single kernel abstraction with both native codegen and vendor-library FFI; multiple dispatch specializes kernels.

**Halide / TVM / Exo.** Algorithm/schedule separation; autoscheduling with learned cost models. Directly informs Osprey's optional schedule layer.

**Chapel.** PGAS language with locales; GPU support via `CHPL_LOCALE_MODEL=gpu`, `forall`/`foreach` loops on GPU sublocales, arrays in unified memory, PTX generation + CUDA driver API. Notable constraints: "PGAS style communication is not available within GPU kernels" and runtime checks are disabled on GPU. Lesson: global-view programming + locale-typed data placement.

**Triton.** Tile-based Python DSL; MLIR-based compiler emitting PTX (and AMD GCN/CDNA); `@triton.jit` kernels operate on tiles via `tl.load`/`tl.store`/`tl.dot` with automatic coalescing/shared-memory/tensor-core scheduling. Since 2026 Triton ships **Gluon** in-tree (`triton.experimental.gluon`) — a lower-level, layout-explicit DSL with first-class Blackwell TMA/mbarrier/TMEM/tcgen05 APIs — as its official path to the newest hardware. Separately, NVIDIA's **CUDA Tile IR has shipped and is open source** (Apache 2.0: MLIR dialect, bytecode, Python bindings, conformance suite, at NVIDIA/cuda-tile), with **cuTile Python** on PyPI (CUDA 13.1+; CUDA 13.2 extends support back to Ampere/Ada). Triton has been named as a potential Tile IR frontend but the stacks remain separate today. Lesson: the tile abstraction is the current sweet spot between thread-level control and full automation; consider it as Osprey's escape-hatch level, and track Tile IR as a possible additional MLIR target dialect.

**JAX / XLA.** Functional transformations (`jit`, `grad`, `vmap`, `pmap`) over a traced functional IR (jaxpr) → StableHLO → XLA (HLO, ~71 optimization passes, operator fusion) → LLVM/PTX or TPU. Lesson: composable functional transformations and whole-program fusion; tracing requires pure functions — a natural fit for Osprey.

**Taichi.** Imperative DSL embedded in Python; JIT via LLVM/SPIR-V; decouples computation from data structures via **SNodes** (sparse/dense hierarchical fields); differentiable; targets CUDA/Vulkan/Metal/OpenGL ES. Lesson: decoupling data layout from computation (AoS↔SoA switch in ≤10 lines) is powerful for performance portability.

**SYCL / Kokkos / Alpaka / RAJA.** C++ single-source portability layers; build-time backend mapping; execution/memory-space abstractions. Lesson for the portability story and space abstractions.

**Slang.** Shading language with **first-class autodiff** (Slang.D, SIGGRAPH Asia 2023); differentiable type system with compile-time safety; multiple backends (SPIR-V, etc.); PyTorch integration. Lesson: autodiff as a type-system-integrated language feature, not a library.

**Legacy/foundational.** CUDA C++ (single-source, thread-level, the performance baseline and interop target), OpenCL (portable, low-level C), OpenACC/OpenMP offload (directive-based, incremental). These define the interop surface and the performance bar.

## Details

### A principled native GPU design for Osprey

**1. Type system extensions.**
- *Address spaces as types.* Introduce space-parameterized array/reference types — conceptually `Buffer[space, a]` with `space ∈ {Global, Shared, Local, Constant}`. Cross-space misuse is a type error. This generalizes OpenCL's address-space qualifiers into HM-inferable type parameters and is strictly safer than Mojo's model.
- *Shapes and indices.* Adopt Dex-style typed indices / statically-tracked shapes to make out-of-bounds and shape-mismatch compile errors and to enable the compiler to reason about parallel `for`/`map`.
- *Device sublanguage.* Define a regular, first-order, statically-shaped subset (like Futhark/Accelerate) that device code must inhabit; full ADTs, closures, and higher-order functions remain in host code and at kernel boundaries. Use the two-flavor/one-AST architecture to formalize this subset without a second language.

**2. Syntactic constructs.** Expose data-parallel combinators (`map`, `reduce`, `scan`, `filter`, `stencil`, `gather`/`scatter`, `segmented_scan`) as first-class, both-flavor surface syntax lowering to canonical AST nodes — mirroring how Osprey already lowers effects flavor-blindly. Provide an optional Triton-style tile block as an escape hatch. Kernel offload should be a *language construct* (an effectful region or a combinator annotation), not a bare library call as in Mojo — this is a concrete ergonomic/safety differentiator.

**3. Effect/ownership story.** Reuse the existing algebraic-effect machinery: define GPU effects and classify them as parallelism-preserving (`Accum`/reduction, à la Dex) vs. parallelism-destroying (general `State`); the effect type of a combinator body determines offload legality, and unhandled GPU effects remain compile errors. Reuse the uniqueness/ownership analysis for device buffers: in-place updates on unique arrays (Futhark-style) for coalesced writes, deterministic frees with no GPU GC, and a `--static-memory`-style guarantee of zero runtime memory management inside kernels. Fiber isolation (share-nothing) maps cleanly onto per-kernel/per-stream isolation.

**4. Compilation strategy — MLIR.** Build the backend on MLIR to match Mojo. Pipeline: Osprey AST → Osprey high-level array dialect (SOACs + shapes + effects) → fusion + incremental-flattening + optional scheduling → `linalg`/`affine`/`vector`/`scf`/`memref` → `gpu` → {`nvgpu`+`nvvm` for NVIDIA; ROCDL for AMD; SPIR-V for Vulkan/WebGPU} → LLVM/PTX/cubin. Support AOT (deployment) and JIT/nvrtc (shape specialization). Reuse Halide/Exo-style algorithm/schedule separation as an optional typed schedule layer with autoscheduling.

**5. CUDA/NVIDIA interop.** Typed FFI wrappers (built on spec §19) over cuBLAS/cuDNN/cuFFT/CUTLASS/Thrust with device-buffer types integrated into ownership. NVIDIA-optimal codegen (tensor cores, wgmma, TMA, warp collectives) via the `nvgpu`/`nvvm` dialects rather than hand PTX, with an inline-PTX escape hatch for the highest-end features (the CuTeDSL/FlashAttention-4 lesson).

### How Osprey differentiates from and improves on Mojo
1. **Safety by construction, not by convention.** Where Mojo chooses "performance over safety," Osprey makes illegal memory-space access, unhandled GPU effects, and aliasing violations *type errors* — using machinery (effects, uniqueness) it already has.
2. **ADTs + pattern matching + HM inference at kernel boundaries** — features Mojo lacks entirely and has deferred past 1.0.
3. **Effect-typed parallelism** (Dex's Accum vs State) gives a principled, checkable purity/parallelism boundary that Mojo's imperative model cannot express.
4. **Kernel launch as a language construct** with effect tracking, versus Mojo's `enqueue_function` library call.
5. **Open, spec-first** versus Mojo's closed compiler (until Fall 2026).
6. **Portability without lock-in** via MLIR's `gpu` dialect, while retaining an NVIDIA-optimal `nvgpu`/`nvvm` path — and Osprey can reuse fast-math and atomics paths where Mojo currently has gaps.

### Key open problems and design tensions
- **Functional purity vs. performance.** Pure combinators are easy to parallelize but need in-place updates for competitive memory behavior; uniqueness types resolve this but (per Futhark's authors) interact awkwardly with other features. Osprey must integrate them with its existing ownership analysis carefully.
- **Nested/irregular data parallelism vs. hardware.** Full flattening can blow up asymptotic work; incremental flattening (multi-version + runtime selection) is the state of the art but complex. Deciding how much irregularity to support on device is the biggest scoping decision.
- **ADTs/sum types on GPUs.** Representing sum types and pointers on SIMT hardware is unsolved in general; the pragmatic answer is to restrict device code to a regular subset — but that limits Osprey's headline ADT advantage to host/boundary code.
- **Portability vs. NVIDIA-optimality.** The MLIR `gpu`→`nvgpu`→`nvvm` stack gives both, but the highest-end NVIDIA features (Blackwell TMA/tcgen05) resist portable abstraction and may require target-specific escape hatches.
- **Ergonomics vs. control.** Implicit combinators are ergonomic but opaque; a Halide/Exo-style optional schedule layer preserves control without cluttering the algorithm — but adds language surface and a scheduling-autotuning research burden.
- **Autodiff design.** Making AD first-class (Dex/Slang-style) with a differentiable-type discipline is a large but competitively important undertaking.

## Recommendations

**Stage 0 — Foundational decisions (now).** Commit to (a) an MLIR-based GPU backend, (b) a Futhark-style regular device sublanguage defined as a typed subset via the existing one-AST architecture, and (c) reusing the effect system + uniqueness analysis for GPU effects and device memory. *Benchmark to revisit:* if MLIR integration cost proves prohibitive relative to a direct LLVM/NVPTX path (as Julia uses), fall back to LLVM GPUCompiler-style codegen — but this concedes Mojo's MLIR advantage.

**Stage 1 — Minimal viable GPU (6–12 mo).** Implement `map`/`reduce`/`scan` combinators over statically-shaped arrays with address-space-typed global buffers; lower to `gpu`→`nvvm`→PTX; AOT only; typed FFI to cuBLAS for a credible matmul. *Threshold to proceed:* match Futhark/CUDA within ~2× on a handful of PPoPP/Rodinia-style benchmarks (stencil, reduction, SGEMM via cuBLAS).

**Stage 2 — Competitive parity (12–24 mo).** Add fusion, incremental flattening, shared-memory/tiling codegen, in-place updates via uniqueness types, the Accum effect, JIT/nvrtc shape specialization, and an optional Halide-style schedule layer. Add tensor-core codegen via `nvgpu`. *Threshold:* close on hand-written CUDA on memory-bound kernels and beat Mojo where it has documented gaps (fast-math, atomics, POD structs on device — Mojo achieves ~87% of CUDA on a memory-bound seven-point stencil).

**Stage 3 — Differentiation (24 mo+).** First-class autodiff (Dex/Slang-informed) with a differentiable-type discipline; portability backends (ROCm/SPIR-V/WebGPU pairing with the existing WASM target); tile-level escape hatch and inline-PTX for Blackwell-class features. *Threshold:* demonstrate a functional, effect-safe, differentiable GPU program that Mojo cannot express safely (e.g., ADT-driven kernel dispatch at boundaries + checked Accum reductions).

**Cross-cutting.** CUDA Tile IR / cuTile is no longer "future": it is open source (Apache 2.0, MLIR dialect + Python bindings) and supported back to Ampere/Ada via CUDA 13.2 — evaluate it as an additional NVIDIA-optimal target dialect alongside `nvgpu`/`nvvm`. Note the active LLVM RFC "Cleaning the GPU dialect" (2026) proposing op reorganization in the MLIR `gpu` dialect — expect churn there. Publish the device sublanguage's type-and-effect rules early to establish academic credibility (PLDI/ICFP/ARRAY workshop); the 2025–2026 wave of typed-GPU papers (Prism/Bundl at PLDI 2026, Kuiper at ARRAY 2025, linear-logic JAX AD at POPL 2026) shows the venue appetite is real.

## Caveats
- **Osprey's GPU features do not yet exist**; the spec marks even memory management as "Not implemented," and effects/resume are only partially implemented. This report is a design foundation, not an evaluation of shipped functionality.
- **Mojo is a fast-moving, immature target.** The ORNL benchmark numbers are from a mid-2025 nightly (v25.5) and are explicitly expected to "evolve as the language matures"; Mojo's closed-compiler and missing-ADT status (Fall 2026 open-source commitment; `match`/enums deferred to 1.x; 1.0 still in beta as of July 31, 2026) was re-verified against Modular's official FAQ, roadmap, and release notes on July 31, 2026, and should be re-verified again before publication or competitive claims.
- **Some sources are secondary or vendor/marketing material** (Medium posts, vendor blogs); the load-bearing technical claims are anchored to primary sources (MLIR docs, PLDI/PPoPP/ICFP/SIGGRAPH papers, NVIDIA PTX ISA docs, the ORNL arXiv paper, Modular's own docs and FAQ).
- **Performance claims are workload-dependent.** "Competitive within 2×" thresholds are heuristics; real positioning requires Osprey-specific benchmarking on named suites (Rodinia, PolyBench, BabelStream).
- **The flattening/ADT-on-GPU frontier is genuinely unsolved**; Osprey's headline ADT advantage will realistically be confined to host and kernel-boundary code in early versions.
