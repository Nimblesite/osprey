# Native mobile delivery [CAST-MOBILE]

Both native apps build and run in the simulator/emulator. All three skins pass native playback journeys on both platforms against a TLS Cast receiver fixture, including exact HTTP media bytes, seek, volume, speed, stop and replay; changing skins preserves the session. Native screenshot goldens gate the ready and restarted player in visible and headless runs on both platforms. CI coverage, broader error/lifecycle cases and physical-device verification remain incomplete.

## Shared boundary [CAST-MOBILE-ABI]

`make -C apps/tests casting-mobile-build TARGET=ios-sim` builds the ARC runtime and the existing casting library. The other targets are `ios`, `android-arm64` and `android-x64`. The output is `build/<target>/libOspreyApp.a`. The native shell must implement `native_slice` and `native_shape`, link the Cast networking services, and drive the resident start/dispatch boundary.

## Verified native progress [CAST-MOBILE-EVIDENCE]

- iOS: the unsigned physical-device app and simulator app link successfully; the real iPhone simulator UI test passes launch, two document-picker cancellations, actual Files selection and import, fixture-file loading, play/pause/resume, seek, volume, speed, stop, replay and restart. Native sliders and speed-menu buttons are verified through XCTest. The receiver checks the requested control values and rejects duplicate slider commands.

- Android: real `Button` and `SeekBar` widgets provide touch, keyboard navigation, native accessibility and focus indicators beneath the shared skin artwork. Programmatic native range updates are paced every two seconds while the canvas keeps animating; focusing or dragging a slider synchronizes it immediately. The keyboard journey opens and cancels the native file picker. ARM64 and x64 JNI libraries link into the APK; the ARM64 emulator discovers a real LAN TV and passes two document-picker cancellations, MP3 import, scene-title verification, play/pause/resume, seek, volume, speed, stop, replay and restart. The fixture verifies exact MP3 bytes over HTTP HEAD and range requests. Android lint passes with warnings treated as errors.
- Both TLS implementations pass live loopback checks for invalid hosts, ports and timeouts, refused TCP connections, unencrypted peers, handshake, fragmented reads, timeout recovery, byte preservation, writes, EOF, cleanup and route selection. Refused TCP connections report the connection error rather than a TLS handshake failure; failed attempts leave the first session slot available. iOS also rejects an empty host before opening a socket. Both full native playback and screenshot suites pass with these transport changes.
- The shared casting suite passes all seven journeys; the Swift host passes 38 regression tests. Native network and media-render runtime suites pass.
- The mobile media runtime uses the existing contract's original-audio fallback because sandboxed apps cannot launch desktop ffmpeg. A native TV visualization renderer is not implemented.

The iOS simulator also passes Home-and-return recovery while casting: the same session remains playing, subsequent controls work, and the fixture rejects any additional media load. This verifies foreground recovery; it does not establish streaming during prolonged device suspension or background audio entitlement behavior.

Android's latest headless journey passes after checking the installed APK for duplicate skin trees and replacing its generated resource cache on launch. Imported media lives outside that cache. The driver resolves the pushed MP3's canonical path and requires a successful native MediaStore scan before selection; shell arguments preserve spaces, apostrophes and Unicode. It verifies that the system picker has actually opened Downloads before touching the file, including when a navigation tap leaves the drawer open. Seven focused driver regressions cover these interactions and fresh accessibility snapshots; the full TLS command and screenshot gates remain unchanged. A terminal automation-process interruption can request up to two additional fresh snapshots; persistent failures and other exit codes still fail, and incomplete or stale dumps are never accepted.

Native scene controls retain their artwork while their hit regions grow to the mobile minimum. iOS explicitly sizes its UIKit sliders because their intrinsic 34-point height otherwise shrank the real view inside a larger SwiftUI frame. Themed controls and Appearance also retain 44-point targets. Android keeps complete visible targets inside viewport edges and removes horizontal-row child margins that clipped buttons. Both suites open the picker by tapping below the old Open File hit region, then pass their existing transport, palette and zero-difference screenshot gates. These checks establish bounds and those interactions; crowded-layout target separation and large-text behavior still need verification.

Both native journeys also select an unavailable localhost receiver, verify its full connection-refused message, change from Poolside to Midnight while retaining the error, and select the working receiver to resume playback without a restart. The fixture requires one additional verified media load and Stop for that recovery; seek, volume and speed command counts remain exact. iOS screenshot checks include the loaded title, Search Again button and receiver menu, so an otherwise successful journey cannot hide unreadable dark-skin text. Native text, buttons and frame ink resolve the theme's text token explicitly; picker labels use its secondary token.

The iOS scene uses a native UISlider that remembers the actual touch endpoint until UIKit emits its change event. UIKit's animated value had continued moving after the finger reached the target. Touch changes now submit that endpoint once; non-touch accessibility changes use the native value. The unchanged real receiver checks pass with a 50.0-second seek and approximately 50% volume. The 38 Swift host regressions also pass with coverage collection enabled; CI coverage thresholds remain to be wired.

The visible iOS suite also discovers a real Bonjour advertisement published by an external test process, rescans, selects it and casts through the advertised hostname and port. This journey omits the injected discovery transcript. Its additional media load passes the same byte, metadata and exact command checks; all three native UI tests and both unchanged screenshot goldens pass. The publisher is terminated when the journey finishes. Permission denial and disappearing receivers remain unverified.

A physical iPhone is paired and has Developer Mode enabled. The current ARM64 bundle was signed with an installed development identity and matching provisioning profile, and `codesign --verify --strict` passed. ## Native screenshot checks [CAST-MOBILE-GOLDENS]

The platform test targets compare both ready and restarted captures with one reviewed reference per platform and pixel width. They crop only the neutral native host and OS bars around the Sherbet player; every player control remains in the comparison. The gate permits at most 0.5% changed pixels overall and 2% in any 64-pixel tile, with a channel difference above 24 counted as changed. The local check has a regression proving that a small missing control fails even when the overall percentage would pass. Native playback and accessibility assertions run before the image checks.

The checked references use an iPhone 17 simulator on iOS 27 at 1206 pixels wide and a Pixel 7 emulator on API 34 at 1080 pixels wide. Start the Android emulator with `-gpu swiftshader_indirect` in both visible and headless modes so the renderer is consistent. The host GPU backend produced an entirely black framebuffer while the control journey passed; the image gate correctly rejected that run. With SwiftShader, both Android modes match the reference exactly. Both iOS modes also match exactly. The visible iOS journey passes in Xcode 27's Device Hub, with native coverage and the same command, palette and screenshot gates. The shared simulator selector opens the chosen device in the selected Xcode's Simulator or Device Hub; headless targets explicitly disable opening a viewer. Tooling regressions cover both installations, paths containing spaces, missing viewers and preservation of device selection.

Use `make -C apps/ios/tests casting-headless` or `make -C apps/android/tests casting-headless` for comparison. Each platform also has `casting-update`, which runs the native journey, rewrites only the ready reference, and checks that restarting still matches it. Review the images under `examples/casting/goldens/<platform>` before committing an update. A missing reference or changed dimensions fails; tests never silently create a baseline. The runner uses the ffmpeg already required for its audio fixture, without an extra image-library dependency.

## Native coverage [CAST-MOBILE-COVERAGE]

The iOS test entry point enables Xcode coverage during the same native journey, then exports [coverage.json](build/ios-test/coverage.json) with `xccov`. It removes the old report before running and publishes the replacement only after checking that the Casting application target has nonzero covered lines and source-file entries. The UI test runner's own counters cannot satisfy that check.

The current report covers 1,689 of 2,853 executable native target lines, approximately 59%. `CastDiscovery.swift` covers 57 of 71 lines after adding real Bonjour discovery and rescanning; the earlier injected-only journey covered 3. This is reported line coverage of the instrumented Xcode target; it excludes the prebuilt Osprey archive and is not proof of branch coverage. Android native coverage collection and required CI coverage gates remain incomplete. No coverage threshold has been lowered.

## Alternate skins [CAST-MOBILE-SKINS]

Android renders the same themed tree with native buttons, popup menus and progress ranges, reusing controls across frames. Both platforms play in Midnight, pause, seek forward, change volume and speed, switch to Poolside without reloading, seek back, resume, stop and replay. The TLS fixture verifies the exact values and command counts. Both platforms change speed while playing. Buttons and pickers validate their complete drawn descriptor before using the current frame revision; this prevents late frames from dropping otherwise unchanged controls, while changed controls remain stale. Its native menu previously restarted its animation on every frame and exceeded the test timeout; unchanged picker descriptors now retain the menu, and a choice is accepted against the current revision only while its complete control binding remains unchanged. Host regressions cover changed ordinals, labels, selected values, choices, removal and invalid keys.

The iOS suite checks Midnight and Poolside background pixels and title ink against their declared palette tokens. All skins declare an `onAccent` colour, and the shared suite enforces a minimum 4.5:1 accent-text contrast in both colour schemes. The Sherbet ready/restart goldens still match exactly. Both hosts now expose an Appearance menu outside the artboard, populated from the same bundled `inputs.skins` choices. Its `skin:<key>` lifecycle event changes only a known bundled skin; unknown keys leave the selection unchanged. The shared playback journey verifies that a host-driven skin change preserves the connection. The iOS native journey changes through Sherbet and Poolside while playing, then changes speed, pauses, stops and replays without additional media loads. Android passes the equivalent live journey, including its speed change while playing. Native time captions and ranges share a two-second update cadence so text changes cannot continuously interrupt accessibility queries; artwork continues animating, and direct slider input retains its full precision. Failure screenshots and the last envelope are retained before teardown. The Appearance menu sits in native host chrome and is checked through native UI assertions; the existing screenshot gate continues to cover the whole Sherbet artboard.
